# YAML-хранилище и перенос данных

`qag serve --data-file ./qag.yaml` использует этот файл как постоянное состояние всего приложения. PostgreSQL для хранения не нужна; HTTP/gRPC/SQL-цели вызовов настраиваются независимо. Обычный `qag` выбирает `./qag.yaml`, если не настроено подключение к БД. Сервер остаётся на переднем плане; Ctrl+C освобождает хранилище и слушатели.

## Два разных файла

`--data-file` / `QAG_DATA_FILE` — YAML с предметными данными. `--config` / `QAG_CONFIG_FILE` — прежний приватный JSON установки с процессными параметрами, PostgreSQL-подключениями и ключом. Конфигурация имеет вид `{"version":1,"values":{"QAG_STORAGE":"yaml","QAG_DATA_FILE":"./qag.yaml"}}`; PostgreSQL-конфигурация содержит соответствующие `QAG_DATABASE_URL`, `QAG_DEMO_DATABASE_URL`, `QAG_SECRET_KEY`.

Флаги переопределяют env, env переопределяет значения config. Явно переданные пустые флаги, неизвестные параметры и лишние аргументы дают код 2 до записи. `--help`/`--version` не открывают конфигурацию или данные. Ошибка явной конфигурации не скрывается переключением backend. Коды переноса: 0 — успех, 1 — ошибка хранения/конфликт, 2 — ошибочные параметры.

## Состав документа

Формат версии 1 — один UTF-8 YAML-документ с `format: qag`, `version: 1`, `data`. Пример пустого состояния:

```yaml
format: qag
version: 1
data: {}
```

При первом serve в нём появится встроенный пример. Основные коллекции:

| Коллекции | Данные |
|---|---|
| `folders`, `testCases` | Каталог, архив, даты, revision и авторский порядок шагов |
| `environments`, `environmentVersions` | Метаданные, открытые переменные и секреты всех версий |
| `resources`, `resourceVersions` | Текущие указатели, все версии настроек, TLS/mTLS, секреты, proto bundles |
| `runs`, `runResourceVersions`, `runSteps` | Снимки, статусы/комментарии, причины сохранения и ключи команд |
| `callAttempts` | Пробные и прогонные попытки, фактические ответы и ключи идемпотентности |
| `runCallVariants`, `variantVersions` | Исследовательские вкладки и все их запросы |
| `runBatches`, `batchItems` | Очереди, порядок и состояния элементов |
| `expectedImages` | Байты base64, формат, размеры, SHA-256 и владельцы изображений |
| `builtinDemo`, `demoItems` | Системные связи и демонстрационные данные |

`steps`, `config`, `snapshot`, `context`, `safeRequest`, `result` и запросы версий сохраняют JSON как literal string внутри YAML. Это сохраняет исторические поля и точные числа без преобразования через float. В SQL NULL отличается от пустой строки. Изображения, PEM и proto-содержимое находятся в самом файле; соседний каталог вложений не нужен.

Секреты сохранённых версий представлены открытыми значениями. Мастер-ключ PostgreSQL, административная конфигурация установки/PKI, роли БД, кеши отчётов/MCP-артефакты и настройки темы браузера не являются предметным состоянием и не экспортируются. Полученные динамические заголовки не восстанавливаются и не добавляются как секреты; сохраняются прежние безопасные результаты.

## Полный перенос

Остановите процессы qag, использующие источник/назначение; PostgreSQL оставьте работающей. Команды берут ту же эксклюзивную блокировку, что сервер, и отказывают для занятого хранилища. Для PostgreSQL нужны её DSN, разрешённое пространство и ключ; demo-DSN для переноса не требуется.

```console
qag data export --storage postgres --output ./export.yaml
qag serve --data-file ./export.yaml
```

Чтобы перенести файл обратно, остановите файловый qag, задайте подключение и ключ целевой PostgreSQL:

```console
qag data import --storage postgres --input ./export.yaml --dry-run
qag data import --storage postgres --input ./export.yaml
```

Для копирования в другой YAML:

```console
qag data import --data-file ./new.yaml --input ./export.yaml --dry-run
qag data import --data-file ./new.yaml --input ./export.yaml
```

Экспорт создаёт новый приватный файл и не заменяет существующий. Импорт сначала проверяет весь вход и объединённый граф. Одинаковые ID/содержимое пропускаются, новые добавляются; отсутствующие во входе записи назначения сохраняются. Различие одного ID, коллизия имени, версии, idempotencyKey, первых сохранённых прогонов или системной связи отменяет весь импорт. CLI выводит безопасные типы/ID и счётчики, не содержимое записей. Повтор импорта до изменения назначения — no-op.

Расходящиеся состояния не синхронизируются по большей revision. Для полной копии выберите новое назначение до первого serve: его встроенный пример ещё не создан и не конфликтует с исходными системными ID. Первый серверный запуск сохраняет импортированные ID и историю, обновляя только текущие системные подключения под выбранный режим/адрес. Пользовательские адреса не переписываются; их достижимость после переноса проверяется отдельно при запуске вызова.

При экспорте PostgreSQL версии секретов расшифровываются её исходным ключом. При импорте они шифруются ключом назначения, которое может иметь другой ключ. Неправильный исходный ключ приводит к отказу. YAML самодостаточен: исходный ключ в нём не хранится и для чтения файла не нужен.

Импорт не запускает Runner, источники заголовков или очередь. Running/queued-состояния сохраняются как данные; следующий serve переводит их в interrupted без повторного внешнего запроса. Прежние idempotencyKey сохраняются. Терминальная история не переоценивается по изменившемуся сценарию.

## Сохранение и ограничения

Связанные изменения фиксируются целым новым файлом с подтверждением записи и атомарной заменой. Начало попытки записывается до внешнего запроса. Сбой до замены оставляет прежнее состояние; авария на границе замены оставляет целый старый либо новый документ. Неопределённое подтверждение отключает новые внешние действия до восстановления; qag не повторяет сам запрос ради записи результата.

Создаваемые данные и временные файлы имеют POSIX 0600 или приватный Windows ACL текущего пользователя. `<file>.lock` — служебный файл блокировки ОС; его существование после аварии не мешает новому запуску. Для переноса достаточно YAML. Ручное редактирование поддерживается при остановленном сервере; обнаруженное изменение открытого файла вызывает конфликт вместо молчаливой перезаписи. Используйте локальную файловую систему с блокировками/атомарной заменой; одновременное редактирование и сетевые папки не поддерживаются.

Предельный документ — 256 MiB, глубина YAML — 64, одна коллекция — 100 000 записей. Сохраняются пределы изображений 10 MiB/20 миллионов пикселей, proto bundles и ответов. Дубликаты ключей, aliases/custom tags, несколько документов, неизвестная версия/поля, неверные связи и повреждённые байты отклоняются. Запись большого состояния требует полной перезаписи YAML; для большой истории с изображениями выбирайте PostgreSQL. Лимит никогда не приводит к молчаливому усечению истории.

В файловом режиме demo HTTP/gRPC читают `demoItems`. SQL-шаг встроенного примера остаётся доступным, сохраняет ошибку `demo_sql_unavailable` и не блокирует остальную очередь либо readiness. Он не использует скрытый SQL-эмулятор или произвольные реквизиты. В PostgreSQL-режиме после подготовки ограниченной demo-роли снова работают все три протокола; прежние YAML-ошибки остаются в истории.

## Что считать резервной копией

YAML — полный логический перенос предметного состояния с открытыми секретами. PDF/text/Markdown/rich — публичный отчёт отдельного прогона с маскированием; он не является импортируемым backup. `pg_dump`/`pg_restore` — прежнее восстановление физического PostgreSQL-формата приложения с исходным ключом и конфигурацией, описанное в [operations.md](operations.md).

Для отката сохраняйте исходные PostgreSQL и ключ/тома. Старый бинарник не читает новый YAML; данные из него сначала перенесите новым CLI в совместимую PostgreSQL с учётом конфликтов. Команды переноса не очищают и не заменяют рабочую БД автоматически.
