# PostgreSQL, ключ и восстановление

Compose запускает один PostgreSQL и использует постоянный том `qag_postgres-data`. Рабочая БД и проверки находятся в `qag` на `127.0.0.1:15432`: рабочие схемы `qag`/`qag_demo`, тестовые — уникальные `qag_test_<runId>`/`<app>_demo`/`<app>_target`. SQL-ресурсы подключаются собственной ролью. Для обычной остановки используйте `docker compose stop`. Команда `down --volumes` удаляет данные.

`scripts/init-local.ps1` создаёт `.local/dev.env` со случайным паролем и отдельным 32-байтовым `QAG_SECRET_KEY` в base64. Повторная инициализация сохраняет рабочий пароль, мастер-ключ и demo-реквизиты. Прежний тестовый URL с БД `qag_test` переводится на рабочее подключение к `qag`; перед изменением создаётся закрытая копия env в `.local`. Ключ не хранится в PostgreSQL. Потеря или замена ключа делает прежние секреты недоступными; автоматической ротации ключа нет. Файл исключён из Git; доступ к нему ограничьте своей учётной записью.

При переходе сначала создайте backup и копию ключа. Выполните `scripts/database.ps1`; он сохранит рабочий том, подготовит PKI и demo-роль. Устаревший контейнер `qag-postgres-test-1` остановите через `docker stop qag-postgres-test-1`. Его том автоматически не удаляется. `-IncludeTests` сохранён как совместимый параметр, второй сервер не запускается.

После проверки общего сервера остановленный старый контейнер можно удалить через `docker rm qag-postgres-test-1` без `--volumes`. Именованный `qag_postgres-test-data` остаётся для явного отката.

Локальная PKI находится в `.local/pki`: CA, серверный сертификат для localhost/loopback и ключи. Подготовка повторяема, повреждённая или истекающая PKI не заменяется молча. Закрытый CA-ключ не монтируется в контейнер. Сервер получает только CA-сертификат, свою пару и HBA; ключ копируется с владельцем postgres и правами 0600. Группа `qag_test_mtls` допускает только cert-auth по TLS. Рабочее SCRAM-подключение сохраняется. Тест выдаёт собственную краткоживущую клиентскую пару и не создаёт PostgreSQL-контейнеров.

Provisioner использует административный доступ для создания и очистки fixtures и хранит runId/nonce/OID/owner в закрытом `qag_test.manifest`. Дочерний qag, demo-reader и SQL-цель получают отдельные NOSUPERUSER/NOCREATEDB/NOCREATEROLE-роли. Очистка сверяет принадлежность, точные имена и OID; рабочие схемы и чужие запуски отклоняются. Аварийно оставшиеся записи требуют проверки тем же manifest перед явной очисткой. Не удаляйте схемы по одному префиксу и не завершайте общие backend-подключения.

`scripts/backup.ps1` включает только `qag` и `qag_demo`, вместе с байтами эталонов, вариантами, их версиями, очередями и попытками. Тестовые пространства в рабочую копию не входят. Тест восстановления делает schema-only dump своих схем, переименовывает исходные схемы в зарегистрированные `_source`, восстанавливает исходные имена и назначает ограниченного владельца. Подмены имён внутри дампа нет.

## Демонстрационная схема и роль

Миграции `003_demo_schema.sql` и `004_builtin_demo.sql` добавляют отдельную схему `qag_demo` с фиксированной записью и метаданные встроенного кейса. Применённые миграции не меняются. Занятая чужими объектами схема вызывает ошибку миграции; приложение не удаляет её и не присваивает существующие данные.

`scripts/database.ps1` собирает `cmd/demo-setup` в `.tools/qag-demo-provision.exe` и подготавливает отдельную LOGIN-роль из `QAG_DEMO_DATABASE_URL`. Реквизиты передаются через окружение процесса. Пароль не передаётся аргументом shell и не выводится. Повторная подготовка сохраняет пароль; чужая роль с тем же именем или роль с повышенными правами отклоняется.

При обычном запуске приложению не нужен `CREATEROLE`. Оно проверяет роль, выдаёт `USAGE` на `qag_demo` и `SELECT` на `qag_demo.items`, затем проверяет подключение отдельным пулом. Чтение схемы `qag`, DML и DDL в demo-схеме запрещены. При проблеме роли или пароля приложение завершается с диагностикой.

Для внешней PostgreSQL администратор один раз запускает подготовку с обоими URL в окружении процесса:

```powershell
go build -o .tools/qag-demo-provision.exe ./cmd/demo-setup
if ($LASTEXITCODE -ne 0) { throw 'Не удалось собрать подготовку роли' }
& .\.tools\qag-demo-provision.exe
if ($LASTEXITCODE -ne 0) { throw 'Не удалось подготовить роль' }
```

На этом этапе `QAG_DATABASE_URL` должен давать права подготовки роли. Затем для запуска qag верните подключение владельца схем приложения. Оба URL должны указывать на одинаковые сервер, порт и БД, но разные имена пользователей. Demo-подключение поддерживает `sslmode=verify-full` (также используется по умолчанию), `sslrootcert`, `sslcert`, `sslkey`; пути к PEM читаются только из доверенной конфигурации запуска. Для локального Compose явно используется `sslmode=disable`.

HTTP демо-сервиса использует основной listener приложения (`/demo/v1/items/{id}`). gRPC слушает `QAG_DEMO_GRPC_ADDRESS`, по умолчанию `127.0.0.1:9091`; допустим только loopback. Порт `0` позволяет тестам выбрать свободный порт. Оба listener останавливаются вместе с qag. Занятый порт вызывает ошибку запуска, а readiness появляется после проверки demo-пула, подготовки системного окружения и запуска gRPC.

Bootstrap выполняется одной транзакцией. Кейс, окружение и ресурсы получают стабильные ID, повторный запуск не создаёт копий. При смене адресов или реквизитов создаётся новая версия соответствующего ресурса; старые снимки и история сохраняются. Начальный bootstrap не выполняет вызовы и не создаёт прогон.

## Резервная копия Compose

Остановите Go-приложение для согласованной точки ручной работы. PostgreSQL оставьте работающим:

```powershell
.\scripts\backup.ps1
# Либо отдельная новая папка:
.\scripts\backup.ps1 -Directory .local/backups/my-backup
```

Скрипт выполняет `pg_dump --format=custom --no-owner --no-acl`, копирует `qag.dump` из контейнера без текстового перенаправления PowerShell и создаёт `qag-secret-key.txt`. Файлы не перезаписываются. Ключ не печатается. Перенесите файл ключа в отдельное защищённое хранилище; дамп и ключ нужны вместе для восстановления секретов.

В дамп входят `qag_demo`, метаданные встроенного кейса, зашифрованный пароль его SQL-ресурса и история прогонов. Роли PostgreSQL не входят в `pg_dump`: отдельно сохраните `.local/dev.env` в защищённом хранилище, чтобы восстановить оба подключения и пароль demo-роли.

Скрипт предназначен для штатной БД `qag-postgres-1`. Для внешней PostgreSQL используйте её `pg_dump` той же основной версии и отдельно сохраните фактический мастер-ключ. Пароли БД приложения и целевого ресурса независимы.

## Восстановление в новую БД

Создайте отдельную пустую БД и проверьте восстановление. Пример для штатного Compose из корня проекта:

```powershell
$qagDocker = & .\scripts\docker-path.ps1
$qagBackup = (Resolve-Path .local/backups/my-backup/qag.dump).Path
& $qagDocker exec qag-postgres-1 createdb -U qag qag_restored
if ($LASTEXITCODE -ne 0) { throw 'Не удалось создать новую БД' }
& $qagDocker cp $qagBackup qag-postgres-1:/tmp/qag-restore.dump
if ($LASTEXITCODE -ne 0) { throw 'Не удалось скопировать дамп' }
& $qagDocker exec qag-postgres-1 pg_restore -U qag -d qag_restored --no-owner --no-acl --exit-on-error /tmp/qag-restore.dump
if ($LASTEXITCODE -ne 0) { throw 'Восстановление не завершено' }
& $qagDocker exec qag-postgres-1 rm -f -- /tmp/qag-restore.dump
```

Сделайте копию `.local/dev.env`. В рабочем файле замените имя базы **в обоих** `QAG_DATABASE_URL` и `QAG_DEMO_DATABASE_URL` на `qag_restored` и установите `QAG_SECRET_KEY` из отдельной копии ключа. Выполните `scripts/database.ps1`: он выдаст demo-роли CONNECT на новую БД. При переносе в новый кластер роль будет создана заново из сохранённых реквизитов. Для внешней БД используйте описанный выше provisioning с правами администратора.

Запустите `scripts/run.ps1`. Bootstrap восстановит права чтения и обновит версию системного SQL-ресурса для новой БД. Проверьте каталог, встроенный пример, его историю и пробный вызов ресурса с секретом. Снимки прежних прогонов сохраняют прежнее подключение. Для возврата остановите qag и верните исходный локальный файл. Для внешней БД измените параметры обоих подключений соответственно.

`TestBackupRestoreCatalogHistoryAndSecret` выполняет настоящий `pg_dump`/`pg_restore` между временными БД тестового контейнера. Проверяются пользовательский и встроенный сценарии, demo-схема, стабильные ID, комментарии, причины сохранения, checksum миграций, расшифровка исходным ключом и отказ с другим ключом. Запуск — `scripts/test-integration.ps1`.

Для отката на бинарник до демонстрационного сервиса восстановите сделанную до обновления копию в отдельную БД. Старый migrator отклоняет неизвестные ему миграции `003`/`004`; удалять схемы или записи миграций ради отката не следует.

## Обновление схемы и откат

Перед обновлением остановите приложение и сделайте резервную копию БД вместе с отдельной копией мастер-ключа. Версия с расширенным редактором применяет шесть миграций: `005_expected_images` добавляет неизменяемые изображения, `006_environment_description` — описание окружения. Первые четыре миграции не изменены; сценарии, версии ресурсов, ciphertext и история сохраняются. Повторный запуск миграций и bootstrap не меняет прежние документы и ID встроенного примера.

Изображения хранятся в PostgreSQL и входят в обычный `pg_dump`; отдельный каталог файлов переносить не требуется. Удаление ссылки из сценария не удаляет байты, нужные прежней истории. Автоматической очистки изображений нет. В backup также входят подписи, описания окружений и настройки HTTP-источников со ссылками на секреты. Полученные динамические токены и полные ответы источников не записываются в БД или дамп. Кэш значений существует только в памяти текущего Go-процесса; после сбоя незавершённые попытки и прогоны становятся `interrupted`, повторных сетевых вызовов нет.

Для отката остановите новую версию и восстановите **копию до обновления** в отдельную пустую БД с исходным мастер-ключом, затем запустите прежний бинарник с обоими URL на эту БД. Старый бинарник отклоняет схему с новыми миграциями. Не удаляйте строки миграций вручную и не направляйте старую версию на обновлённую БД. Изменения, выполненные после выбранной резервной копии, в такой откат не входят.

## Диагностика

| Симптом | Действие |
|---|---|
| Docker Engine недоступен | Запустите Docker Desktop, дождитесь Linux Engine |
| Virtual Machine Platform not enabled | Включите компонент Windows и перезагрузите компьютер согласно [Microsoft](https://learn.microsoft.com/en-us/windows/wsl/install-manual#step-3---enable-virtual-machine-feature) |
| PostgreSQL недоступна | Проверьте контейнер, порт, БД и пароль; пароль существующего тома сам не меняется |
| Не удалось подготовить схему | Нужны права создания схемы/таблиц/ICU collation; используйте штатный Compose |
| Схема несовместима | Запустите соответствующую версию бинарника; применённые миграции не редактируйте |
| Другой экземпляр использует БД | Оставьте один Go-процесс; второй не меняет данные первого |
| Адрес занят | Освободите порт или задайте другой loopback `QAG_ADDRESS` |
| gRPC-порт недоступен | Освободите `127.0.0.1:9091` или задайте другой loopback `QAG_DEMO_GRPC_ADDRESS` |
| Ошибка demo-роли или подключения | Проверьте оба URL, выполните подготовку БД и роли; повышенные права и чужие роли не перенастраиваются автоматически |
| Не удалось расшифровать секреты | Верните исходный `QAG_SECRET_KEY` |
| Результат не подтверждён PostgreSQL | Восстановите БД; повторяется только запись результата, не внешний вызов |
| `interrupted`, отмена или тайм-аут | Проверьте внешний эффект в целевой системе перед новой явной попыткой |

`GET /api/v1/health` показывает readiness при доступных основной БД, demo-пуле и работающем gRPC. Сервер принимает локальные Host и доверенный Origin; для Vite нужен `QAG_DEV_ORIGIN`. Логи не содержат строки подключения, мастер-ключа или тела протокольного запроса.
