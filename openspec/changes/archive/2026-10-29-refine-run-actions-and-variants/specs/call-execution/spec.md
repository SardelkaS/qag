## MODIFIED Requirements

### Requirement: Выполнение unary gRPC

gRPC-блок SHALL задавать полное имя сервиса и метода, JSON-сообщение запроса и метаданные; ожидаемый gRPC-код SHALL задаваться для исходного блока, а исследовательский вариант SHALL выполняться без ожидания. Приложение SHALL получать описание сообщения через server reflection либо загруженный набор .proto со всеми импортами. Результат SHALL включать gRPC-код, сообщение статуса, ответ в JSON, начальные метаданные и trailers при их наличии. Streaming-метод и недоступное описание MUST приводить к явной ошибке до вызова прикладного метода.

#### Scenario: Сервер без reflection
- **WHEN** reflection недоступен, но для ресурса загружены корректные `.proto` со всеми импортами
- **THEN** unary-запрос выполняется по загруженному описанию и результат отображается в JSON

#### Scenario: Неожиданный streaming-метод
- **WHEN** пользователь выбирает метод с потоком сообщений
- **THEN** приложение показывает, что первая версия поддерживает только unary, и не запускает метод

#### Scenario: Ожидаемый gRPC-статус ошибки
- **WHEN** сервер возвращает `NOT_FOUND`, а этот код указан в ожидании
- **THEN** код участвует в обычном сравнении, а отсутствие сообщения ответа не подменяется сетевой ошибкой

#### Scenario: Вариант без ожидаемого кода
- **WHEN** исследовательский unary-вызов не задаёт ожидаемый gRPC-код и сервер вернул NOT_FOUND
- **THEN** попытка сохраняет фактический код и сообщение без требования ожидания и без автоматического сравнения

### Requirement: Связь результата с конкретной попыткой

Результат SHALL содержать протокол, версию блока, окружение и обезличенные сведения о разрешённом ресурсе. Для исследовательского вызова SHALL дополнительно фиксироваться вариант и его сохранённая версия параметров. Поздний результат другой попытки или вкладки MUST не подменять выбранный результат. Во время прогона все попытки SHALL привязываться к его снимку; сравнение SHALL выполняться с ожиданием исходного блока только для исходных попыток. Принадлежность к исследовательскому варианту SHALL определяться сохранённой сервером связью, а его выполнение MUST не зависеть от унаследованных ожиданий. Проверки запроса и защита секретов SHALL сохраняться для обоих видов попыток. Выполнение блока из редактора MUST не создавать самостоятельный прогон тест-кейса.

#### Scenario: Изменение ожидания после старой попытки
- **WHEN** пользователь изменил ожидание в редакторе после получения результата
- **THEN** старый результат помечается как относящийся к прежней версии и не сравнивается молча с новым ожиданием

#### Scenario: Пробный запуск в редакторе
- **WHEN** пользователь запускает блок без начала прогона
- **THEN** интерфейс показывает результат для проверки блока, а признаки первого и первого успешного прогона тест-кейса не изменяются

#### Scenario: Поздний ответ варианта
- **WHEN** пользователь выбрал другую вкладку до получения результата исследовательской попытки
- **THEN** результат относится к своему варианту и версии и не подменяет результат выбранной вкладки

#### Scenario: Нельзя отключить исходное сравнение
- **WHEN** клиент пытается обозначить обычную исходную попытку как исследовательскую без сохранённого варианта
- **THEN** сервер не отключает её проверки ожидания и не меняет официальный результат
