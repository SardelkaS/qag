## Context

См. `proposal.md` для мотивации и `specs/` для наблюдаемого поведения. Текущее состояние проверено по реализации и основным спецификациям:

- `resources.Environment.Variables` и API переменных используют `map[string]string`. HTTP-определения уже существуют в `Config.Variables` отдельных ресурсов; `ResourceVariables.tsx` умеет переключать literal/http и использует общий `HTTPSourceFields`.
- `catalog.HTTPHeaderSource` содержит `prefix`, но не `suffix`, и форматы тела `none`, `text`, `json`. `prepareRequestHeaders` подставляет текстовое тело без form-кодирования, `Runner.http` отправляет его байты напрямую.
- `execution.resolveVariables` получает HTTP-переменные после регистрации попытки. Его кеш сейчас привязан к версии ресурса; простое копирование определения окружения в каждый ресурс нарушило бы общее получение `per_run`.
- `ResourceForm.submit` уже отправляет полный `config`, локальные переменные и изменения секретов одним запросом. PostgreSQL `SaveResource` создаёт версию в транзакции; YAML использует `Store.Update`. Конкретная причина сообщённой потери настроек пока не подтверждена. При этом чтение PEM/proto асинхронно и сейчас не блокирует сохранение на уровне всей формы.
- Сохранение переменных окружения отделено от его имени/описания. Публичные ответы возвращают имена секретов; снимок прогона хранит ID версии окружения. `dataset` использует YAML v2, принимает прежний v1 и сравнивает defaults без переписывания raw JSON истории.

## Goals / Non-Goals

**Goals:**

- Расширить существующий конвейер подготовки/исполнения, сохранив регистрацию до сети и одинаковое поведение UI/MCP, пробных вызовов, очередей и исследовательских вариантов.
- Разделить владельца определения, контекст секретов и ключ кеша для переменных окружения и ресурса.
- Сделать сериализацию полного draft и подтверждение сохранения проверяемой границей между UI и обоими хранилищами.

**Non-Goals:**

- Цепочки HTTP-переменных, автоматическое обновление просроченного токена, OAuth-мастер, импорт curl, multipart, чтение `@file` как в curl и извлечение из HTTP-заголовков ответа. Получаемый скаляр по-прежнему выбирается JSON Pointer.
- Новый формат form-urlencoded для обычных блоков тест-кейса: в этом изменении он относится к HTTP-источникам значений.
- Автоматическое изменение переменных окружения при сохранении отдельного ресурса или переписывание старых версий и результатов.

## Decisions

### 1. Добавочное поле HTTP-переменных окружения

Сохранить `variables: map[string]string` без изменения и добавить `httpVariables: map[string]HTTPHeaderSource` в публичное окружение, команду его переменных и версию окружения в обоих backend. В PostgreSQL нужна новая миграция `010_environment_http_variables.sql` с отдельным JSONB-полем, по умолчанию пустым. В YAML та же информация хранится в записи `EnvironmentVersion`.

Одна команда переменных применяет literal-набор, HTTP-набор и keep/replace/clear секретов с одной revision. Пропущенное `httpVariables` при обновлении сохраняет существующий набор, `{}` явно очищает его; создание без поля даёт пустой набор. Транспорт различает отсутствие и явную передачу; `null` не используется как скрытое удаление и отклоняется. Обновление имени/описания копирует все определения и секреты в новую версию. Пустые имена новых строк отфильтровываются до проверки вложенного источника и транспортной схемы, как для существующих локальных переменных.

Форма переменных использует общие строки literal/http, разделяя их в два поля только при сборке команды. Проверки пересечений учитывают literal/http/secret имена окружения и определения текущих ресурсов; проверка повторяется при сохранении ресурса и при подготовке. Исторические версии не используются как запрет на новое имя, но продолжают исполняться в собственном старом контексте.

Альтернатива — заменить строки окружения объектами `VariableDefinition`: это ломает API, прежние клиенты и перенос. Единственная карта всех уровней также скрыла бы владельца источника.

### 2. Источник окружения получает независимый контекст и кеш

Расширить разрешённый контекст в `internal/resources` определениями окружения, его ID/версией, статическими значениями и секретами отдельно от эффективного контекста целевого ресурса. Источник окружения видит только статические значения/секреты своего окружения; локальный источник сохраняет прежний доступ к статическим значениям и разрешённым секретам окружения и ресурса. Даже одноимённый секрет целевого ресурса не меняет источник окружения. HTTP-зависимости любого уровня, в том числе через статическую ссылку, запрещены.

`RequiredVariables` определяет только реально необходимые определения после применения перекрытий общих заголовков. `resolveVariables` использует общий механизм получения, но выбирает владельца и контекст. Ключ кеша включает область, версию владельца, имя и digest определения; область прогона остаётся внешней границей. Для окружения ключ не содержит ID целевого ресурса, поэтому `per_run` делится между HTTP/gRPC/SQL того же прогона. Для ресурса сохраняется независимый ключ его версии. В trace добавляется безопасный признак области определения, без выбранного значения.

Чистая подготовка остаётся до `BeginAttempt`, HTTP выполняется после устойчивого начала попытки. Сохраняются общий deadline/отмена, точное скалярное извлечение, отсутствие redirects/автоповторов и получение только нужных значений. Ошибки не становятся кешем. Для пробного запуска область ограничена попыткой; перезапуск не восстанавливает кеш и не возобновляет сеть. Полученные строки считаются непрозрачными данными и не интерпретируются повторно как `${...}`.

Альтернатива — хранить полученное значение в окружении либо копировать источник в ресурсы: первая раскрывает временные секреты и меняет версии, вторая выполняет лишние запросы и допускает разные учётные данные.

### 3. Структурированные поля формы вместо ручного тела

В общий `HTTPHeaderSource` добавить `bodyMode: "form"` и `form: []KeyValue`. Поля имеют исходные неэкранированные значения. При подготовке разрешённые подстановки выполняются в именах и значениях; секреты разрешены только в значениях, как в теле источника. Затем исполнитель кодирует каждую пару через стандартное UTF-8 form-кодирование и соединяет их в исходном порядке. Список сохраняет повторные имена и пустые значения. Полностью пустая пара игнорируется; непустое значение при пустом имени даёт ошибку. Имена, оставшиеся пустыми после подстановки, также отклоняются.

Кодирование выполняется ровно один раз: `+`, `&`, `=`, `%` и Unicode передаются как данные, пробел кодируется `+`. В form-режиме `body` пуст; в остальных режимах список `form` пуст. UI может держать несохранённые значения разных режимов локально, но команда включает только активный режим. Противоречивое тело из API/MCP отклоняется. Query остаётся независимым.

Если Content-Type не задан, устанавливать `application/x-www-form-urlencoded`. Явный тип проверять как тот же media type с необязательным UTF-8 charset; повторные Content-Type и несовместимый тип отклонять до сети, включая тип после подстановки. Редактор показывает поля формы вместо текстового textarea. Прежние text/json не получают нового кодирования. Расширение применяется к источникам заголовков и переменных обоих уровней, без нового транспорта или зависимостей.

Альтернатива — требовать ручной percent-encoding: она сохраняет текущую ошибкоопасную настройку и не кодирует подставленный секрет. Неявное кодирование всего текстового тела разрушает разделители и старые конфигурации.

### 4. Необязательный suffix в общем источнике

Добавить строковое `suffix` с пустым default. В общем редакторе оставить совместимый `prefix`, показав поля «Текст перед значением» и «Текст после значения» с подсказкой о значимых пробелах. Сборка `prefix + scalar + suffix` применяется одинаково к заголовкам и переменным, продолжая уже существующую поддержку prefix у переменных.

Префикс и суффикс поддерживают прежние допустимые статические подстановки без секретов и без ссылок на HTTP-переменные; для источника окружения действует его независимый контекст. Сохраняются пробелы и пустые строки, без автоматического `trim`. Конфигурация/подготовка отвергают CR/LF в текстовых обрамлениях; итоговый заголовок также проходит существующие ограничения HTTP/gRPC. Сырой скаляр и итог целиком включаются в маскирование вместе с URL/JSON-экранированными формами. Form-кодированные сохранённые секреты также не попадают в диагностику. В кеш можно помещать только успешное значение в своей области; маски уже полученных значений сохраняются до закрытия области даже после ошибки следующего этапа.

Альтернатива — произвольный шаблон с новым маркером результата: он добавляет язык выражений и требует миграции уже сохранённого prefix. Два строковых поля решают запрос пользователя без изменения старых определений.

### 5. Полный draft и одна подтверждённая версия ресурса

Сохранить существующую одну серверную операцию; сначала закрепить сценарий одновременного изменения всех применимых разделов и повторного открытия в `ResourcesPanel`/E2E. Проверять не только отображение до закрытия, но и payload, ответ сервера, новое чтение, reload и перезапуск обоих backend. Не считать причину потери установленной до воспроизведения; если проблема обнаружена в сборке/нормализации, исправлять именно этот участок.

Явно собирать команду из одного согласованного состояния: config с общими заголовками и всеми вложенными полями, resourceVariables, секретные изменения, TLS и proto. До submit дожидаться всех выбранных файлов, включая PEM внутри HTTP-источника. Ошибка файла не заменяет прежнее значение. На время чтения/отправки блокировать сохранение и исключить позднее обновление уже сменённого ресурса старым чтением файла.

Сервер валидирует весь config и эффективный контекст, объединяет секреты и фиксирует одну новую версию в существующей транзакции/`Store.Update`. Не выполнять HTTP-источники при сохранении. При отказе остаются прежняя версия и клиентский draft; сообщение различает ошибку записи и конфликт revision. После успеха использовать возвращённую revision и полный config; обновление списка не должно терять вложенные настройки. Повторное чтение не возвращает значения write-only секретов. Переменные окружения сохраняются своим endpoint и в команду ресурса не входят.

Альтернатива — отдельные запросы сохранения заголовков, переменных и TLS: это допускает частичные версии и требует от пользователя нескольких подтверждений.

### 6. YAML v3 и добавочная совместимость

Новая структура `EnvironmentVersion` требует YAML v3; `dataset` читает v1/v2/v3, пишет v3. Старые версии получают пустые HTTP-определения окружения, а источники без suffix/form сохраняют прежнее поведение. Строгие проверки неизвестных полей и лимиты не ослабляются. Defaults при сравнении добавляются только в копии соответствующих предметных полей, не в произвольный JSON пользовательских тел и не в сохранённые raw snapshots/results.

Обновить PostgreSQL export/import и файловое хранилище: переносится каждая версия определения и ссылки прогонов на неё. Идентичность старых записей учитывает пустые новые поля, реальное отличие источника/суффикса/формы даёт атомарный отказ всего импорта по прежним правилам. Не получать значения при чтении, переносе или восстановлении. Текущие 001–009 миграции, исторические ID и JSON остаются неизменными.

Альтернатива — расширить v2 без смены версии: старый строгий decoder не сможет прочитать новое поле, а документ будет заявлять прежнюю совместимость.

### 7. API/MCP и проверяемые примеры

Расширить существующий `qag_variables_set` и команды ресурсов, не вводя дублирующие инструменты. Обновить входные/выходные контракты, обработку пустых строк до проверки схем, генератор OpenAPI/MCP, TS-типы и встроенное руководство. Пример показывает POST-форму с `client_secret=${CLIENT_SECRET}`, Pointer `/access_token`, `per_run` и Authorization с `Bearer `; отдельный пример показывает suffix. Указывать, что HTTP-определение сохраняется, а полученное значение не читается через конфигурацию.

Альтернатива — отдельный MCP-only конвейер: он разойдётся с UI по версиям, кешу и сохранению. Проверки должны использовать те же предметные операции и оба поддерживаемых поколения MCP.

## Risks / Trade-offs

- [Смешение секретов ресурса и окружения] → отдельный контекст источника окружения и тест с разными одноимёнными секретами нескольких ресурсов.
- [Повторное получение общего токена или утечка кеша между прогонами] → ключ владельца/версии, независимость пробных запусков и проверки счётчика реальных запросов при очередях и повторах команд.
- [Повреждение специальных символов или повторное кодирование] → тесты получателя формы с `+`, `&`, `=`, `%`, Unicode, пустыми и повторными значениями; текстовый режим остаётся побайтовым.
- [Ложное полное сохранение при незавершённом чтении файла или конфликте revision] → единый submit, учёт всех pending reads, сохранение draft при ошибке и проверки повторного чтения после reload/restart.
- [Ложные конфликты старого YAML либо изменение истории] → defaults только в копии для сравнения, round-trip v1/v2/v3 и контроль неизменности raw JSON.
- [Устаревшие примеры MCP и встроенный frontend] → генерация контрактов, проверка примеров по схемам и обновление встроенного bundle вместе с исходниками при реализации.

## Migration Plan

1. Добавить миграцию 010 с пустым JSONB-набором HTTP-источников во всех существующих версиях окружения. Прежние столбцы, номера версий, config и снимки не менять.
2. Ввести чтение v1/v2/v3 и экспорт v3; простое чтение/экспорт не меняет исходный файл, первая подтверждённая запись переводит его в v3 атомарно.
3. Расширить оба repository, контракты и исполнитель, затем UI и сгенерированный bundle. Старые клиенты без новых полей продолжают работать с прежними значениями и не очищают источники окружения.
4. Проверить общую авторизацию между ресурсами/протоколами, текст с обеих сторон, форму и полное сохранение на изолированном состоянии PostgreSQL/YAML. Действующие пользовательские данные и секреты для проверок не переопределять.
5. Откат бинарника допустим только вместе с копией данных до появления новых определений. Старый qag не читает v3 и не должен исполнять новые источники в несовместимом формате; для PostgreSQL добавочный столбец можно оставить, но не использовать старый исполнитель для новых данных. Автоматического удаления столбца или переписывания истории нет.
