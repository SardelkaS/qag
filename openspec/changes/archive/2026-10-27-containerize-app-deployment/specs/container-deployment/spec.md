## Purpose

Контейнерное развёртывание позволяет собрать и запустить qag вместе с PostgreSQL средствами Docker Compose, сохраняя локальный доступ из браузера, постоянные данные и повторяемые команды эксплуатации.

## ADDED Requirements

### Requirement: Самодостаточный контейнер приложения

Репозиторий SHALL предоставлять Dockerfile для сборки Linux-образа qag из исходников с зависимостями, закреплёнными в проекте. Готовый образ SHALL содержать Go-приложение, встроенный Web UI, иконки, шрифты и необходимые доверенные CA. Сборка и штатный запуск MUST не требовать Go, Node.js, PowerShell или локальной предварительной сборки на хосте. Runtime SHALL запускать приложение непривилегированным пользователем. Локальные ключи, env-файлы, дампы, зависимости хоста, Windows-артефакты и Git-метаданные MUST не попадать в образ либо передаваться как секретные build arguments.

#### Scenario: Сборка чистого checkout
- **WHEN** пользователь с установленными Docker и Compose собирает приложение из чистой копии репозитория
- **THEN** образ собирается без локального Go/Node.js и предоставляет встроенный UI с сохранённой иконкой и шрифтами

#### Scenario: Локальные данные рядом с исходниками
- **WHEN** в рабочей копии есть приватная конфигурация, backup и готовый Windows-бинарник
- **THEN** контейнерная сборка не включает эти данные в build context и образ

### Requirement: Единый жизненный цикл Compose

Штатный Compose SHALL запускать приложение qag и один PostgreSQL в отдельных контейнерах одной установки. Команда `docker compose up --build -d --wait` на новой установке SHALL подготавливать конфигурацию, PostgreSQL и отдельную ограниченную demo-роль до готовности приложения. Подготовительные операции MUST быть повторяемыми и MUST не создавать отдельный постоянно работающий демонстрационный сервис или тестовый PostgreSQL. Приложение SHALL иметь проверку готовности; ошибка подготовки либо недоступная БД MUST не давать ложный healthy. Обычная остановка и пересоздание MUST сохранять постоянное состояние. Завершение контейнера SHALL доходить до процесса qag и освобождать его слушатели и подключения.

#### Scenario: Запуск нового стенда
- **WHEN** пользователь выполняет документированную Compose-команду без прежней конфигурации и данных
- **THEN** qag и PostgreSQL запускаются, подготовка завершается автоматически, а контейнер приложения становится healthy после миграций и bootstrap

#### Scenario: Задержка либо отказ PostgreSQL
- **WHEN** PostgreSQL ещё не готов или подготовка demo-роли завершилась ошибкой
- **THEN** приложение не объявляется готовым, а диагностика позволяет определить неуспешный этап без раскрытия реквизитов

#### Scenario: Остановка и повторный запуск
- **WHEN** пользователь останавливает Compose и затем запускает его снова
- **THEN** контейнеры завершаются управляемо, данные и конфигурация сохраняются, а незавершённые внешние вызовы автоматически не повторяются

### Requirement: Опубликованный локальный HTTP-порт

Compose SHALL публиковать HTTP-порт приложения на `127.0.0.1:8080` по умолчанию и позволять явно выбрать другой свободный порт хоста. Из браузера SHALL быть доступны UI, API и встроенный демонстрационный HTTP через этот опубликованный адрес. Контейнерный listener SHALL быть доступен перенаправлению Docker, а внутренний порт SHALL оставаться независимым от опубликованного. Проверки Host, Origin и CSRF MUST учитывать выбранный адрес и MUST не заменяться wildcard-разрешением либо доверием произвольным forwarded-заголовкам. Штатное отображение портов MUST не открывать приложение на всех интерфейсах хоста; демонстрационный gRPC MUST не требовать публикации отдельного порта.

#### Scenario: Доступ из браузера
- **WHEN** Compose сообщает готовность установки с настройками по умолчанию
- **THEN** `http://127.0.0.1:8080` открывает приложение, а действия сохранения и запуска проходят обычную проверку локальной сессии

#### Scenario: Другой порт хоста
- **WHEN** пользователь задаёт внешний HTTP-порт 18088
- **THEN** UI и изменяющие API-команды работают через `http://127.0.0.1:18088` без правки кода и без отключения проверки Origin

#### Scenario: Посторонний источник
- **WHEN** запрос к опубликованному приложению имеет посторонний Host, Origin либо неверный CSRF-токен
- **THEN** сервер отклоняет его до изменения данных или внешнего вызова

### Requirement: Постоянная приватная конфигурация

Мастер-ключ, пароли БД и demo-роли и локальная PKI SHALL сохраняться вне образа и PostgreSQL в постоянном состоянии установки. Новая установка SHALL получать случайные реквизиты, а повторная подготовка MUST сохранять прежние значения. Runtime приложения SHALL получать конфигурацию только для чтения; PostgreSQL MUST не получать приватный ключ CA. Подготовка MUST обнаруживать неполную или повреждённую конфигурацию и MUST не заменять ключи либо ослаблять TLS автоматически. Если PostgreSQL уже содержит данные, а исходная конфигурация отсутствует, запуск MUST потребовать её импорт или восстановление до генерации новых реквизитов.

#### Scenario: Пересоздание контейнеров
- **WHEN** пользователь пересобирает образ и пересоздаёт контейнер qag на прежних томах
- **THEN** мастер-ключ и пароли остаются прежними, сохранённые секреты расшифровываются, а история и эталоны доступны

#### Scenario: Есть БД, нет ключа
- **WHEN** существующий PostgreSQL-том подключён без сохранённой конфигурации
- **THEN** подготовка прекращается с указанием необходимости импорта или восстановления и не генерирует замену мастер-ключа

#### Scenario: Повреждённая PKI
- **WHEN** конфигурация содержит неполную или недействительную PKI
- **THEN** запуск сообщает причину без автоматической смены CA и без отключения проверки сертификатов

### Requirement: Переход существующей установки и резервные копии

Документированный переход с нативного qag SHALL использовать существующий PostgreSQL-том и явный импорт исходной локальной конфигурации, включая мастер-ключ, пароли и PKI. Импорт MUST не менять пароль существующей БД, исходные файлы и пользовательские сценарии, ресурсы, шифротексты либо снимки истории. Системные подключения SHALL получать адреса, пригодные внутри контейнера, сохраняя идентичность встроенного кейса и прежние версии. Несовместимая либо противоречивая конфигурация MUST отклоняться без частичной замены данных. Операционная инструкция SHALL описывать backup БД и отдельной приватной конфигурации средствами Docker и восстановление с исходным ключом; обычные команды остановки MUST не удалять тома.

#### Scenario: Импорт прежних реквизитов
- **WHEN** пользователь останавливает нативный процесс, импортирует исходную конфигурацию и запускает контейнеры на прежнем томе
- **THEN** кейсы, окружения, секреты, изображения и история сохранены, а встроенный пример работает с внутренними адресами контейнерной установки

#### Scenario: Конфликт конфигураций
- **WHEN** импортируемый ключ или пароль противоречит уже сохранённой конфигурации контейнерной установки
- **THEN** операция прекращается без перезаписи ключа, смены пароля или удаления данных

#### Scenario: Восстановление установки
- **WHEN** пользователь восстанавливает PostgreSQL-backup и отдельную копию конфигурации с исходным ключом по инструкции
- **THEN** секреты читаются, прежняя история и эталоны доступны, а незавершённые вызовы не возобновляются автоматически

### Requirement: Команды Makefile

Корневой Makefile SHALL предоставлять цели `help`, `init`, `build`, `up`, `down`, `restart`, `logs`, `ps` и `import-local`. Они SHALL вызывать тот же Compose-проект, образ, порты и постоянное состояние, что и прямые команды Docker. Для штатного запуска через Make SHALL требоваться только Docker Compose и GNU Make; рецепты MUST не зависеть от POSIX-утилит либо обязательного PowerShell. Цель `up` SHALL обеспечивать сборку и ожидание готовности; `down` MUST сохранять тома. Ошибка Docker MUST давать неуспешный код Make без ложного сообщения об успешном запуске. `help` SHALL кратко описывать цели без запуска сервисов и раскрытия секретов.

#### Scenario: Запуск через Make
- **WHEN** пользователь выполняет `make up`
- **THEN** получается та же готовая локальная установка, что при прямом `docker compose up --build -d --wait`

#### Scenario: Остановка через Make
- **WHEN** пользователь выполняет `make down` и затем `make up`
- **THEN** постоянные данные, ключ и реквизиты сохраняются

#### Scenario: Нет Make либо Docker недоступен
- **WHEN** GNU Make не установлен либо Docker Engine недоступен
- **THEN** README предоставляет прямую альтернативу без Make, а ошибка Docker при вызове Make остаётся видимой и возвращает неуспешный код
