## Purpose

Встроенный демонстрационный сервис предоставляет постоянную локальную цель для HTTP-, gRPC- и PostgreSQL-проверок, чтобы пример qag можно было пройти сразу после настройки приложения.

## ADDED Requirements

### Requirement: Единый локальный демонстрационный сервис

qag SHALL предоставлять демонстрационные HTTP- и unary gRPC-интерфейсы как часть обычного запуска приложения. Оба интерфейса MUST читать одну демонстрационную запись из PostgreSQL и возвращать согласованные идентификатор, название, статус и точную сумму. Демонстрационные адреса SHALL быть доступны только через loopback. Отдельный запуск сервиса пользователем MUST не требоваться.

#### Scenario: Согласованное чтение через два протокола
- **WHEN** пользователь запрашивает существующую демонстрационную запись через HTTP и gRPC
- **THEN** оба ответа содержат одинаковые значения из одной записи PostgreSQL

#### Scenario: Запуск штатной сборки
- **WHEN** пользователь запускает настроенную готовую сборку qag
- **THEN** демонстрационные HTTP и gRPC доступны вместе с приложением без дополнительного процесса или контейнера

### Requirement: Отдельная постоянная демонстрационная схема

Демонстрационные таблицы и начальная запись SHALL находиться в отдельной схеме `qag_demo` существующей БД qag. Перезапуск SHALL сохранять эту схему и данные. Инициализация MUST не удалять и не заменять пользовательские папки, сценарии, ресурсы или историю. Демонстрационные публичные методы SHALL читать данные; их выполнение MUST не изменять демонстрационную запись.

#### Scenario: Добавление в существующую установку
- **WHEN** приложение с пользовательскими данными впервые запускается после обновления
- **THEN** схема и начальная демонстрационная запись появляются, а существующие пользовательские записи сохраняются

#### Scenario: Повторные обращения
- **WHEN** пользователь многократно вызывает демонстрационные методы и перезапускает qag
- **THEN** начальная запись остаётся доступной с теми же значениями без очистки или ручного сброса

### Requirement: Контракт демонстрационного HTTP

HTTP SHALL предоставлять `GET /demo/v1/items/{id}`. Для `example-001` ответ SHALL иметь статус 200 и JSON с полями `id`, `name`, `status`, `amount`. `amount` MUST передаваться десятичной строкой без округления. Отсутствующая запись SHALL давать 404. Недоступная БД SHALL давать явную ошибку доступности; сервис MUST не подменять чтение БД статическим успешным ответом.

#### Scenario: Известная запись
- **WHEN** выполняется `GET /demo/v1/items/example-001`
- **THEN** HTTP 200 возвращает `id=example-001`, `name=Локальный пример qag`, `status=ready` и `amount=9007199254740993.125`

#### Scenario: Отсутствующий идентификатор
- **WHEN** выполняется запрос для `missing-item`, отсутствующего в демонстрационной таблице
- **THEN** сервис отвечает 404, пригодным для обычного сравнения отрицательного результата

### Requirement: Контракт демонстрационного gRPC

gRPC SHALL предоставлять unary-метод `qag.demo.v1.DemoService/GetItem` с идентификатором записи в запросе. Ответ SHALL содержать те же поля и точную сумму строкой, что и HTTP. Описание сервиса SHALL быть доступно через server reflection и поставляемый `.proto`. Отсутствующая запись SHALL давать `NOT_FOUND`; недоступная БД SHALL давать `UNAVAILABLE` без раскрытия реквизитов.

#### Scenario: Получение через reflection
- **WHEN** gRPC-блок вызывает `GetItem` с `{"id":"example-001"}` и использует reflection
- **THEN** результат имеет код `OK` и JSON-представление той же записи, что вернул HTTP

#### Scenario: Ожидаемое отсутствие записи
- **WHEN** gRPC-блок вызывает `GetItem` с `{"id":"missing-item"}`
- **THEN** результат имеет код `NOT_FOUND` и может совпасть с таким ожиданием

### Requirement: Готовый сценарий трёх протоколов

qag SHALL автоматически подготовить один встроенный кейс «Пример: HTTP, gRPC и PostgreSQL» с описаниями действий и заполненными запросами и ожиданиями. Кейс SHALL проверять положительные HTTP/gRPC-ответы, SQL-чтение той же записи, ожидаемые HTTP 404 и gRPC `NOT_FOUND`, а также отдельное ручное действие. Первый и последующие прогоны SHALL использовать обычные правила ручных статусов, сравнения, снимков и сохранения истории.

#### Scenario: Первое прохождение
- **WHEN** пользователь открывает встроенный пример, выполняет все вызовы, отмечает ручные шаги как пройденные и завершает прогон
- **THEN** положительные и ожидаемые отрицательные вызовы совпадают, прогон получает `passed` и сохраняется по обычным правилам первых прогонов

#### Scenario: Повторное прохождение без подготовки
- **WHEN** пользователь начинает следующий прогон того же примера
- **THEN** он использует готовые ресурсы и те же стабильные данные без ручного редактирования запроса или БД
