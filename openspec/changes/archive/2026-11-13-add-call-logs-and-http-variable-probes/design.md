## Context

Мотивация и согласованный состав изменения описаны в proposal.md. Текущие точки расширения:

- `internal/service/engine.go` устойчиво создаёт попытку до сети, использует request gate для отмены и повторяет только запись результата при отказе хранилища. В `internal/execution` уже есть HTTP/gRPC/SQL, единые лимиты и маскирование.
- `execution.Attempt.Request` содержит безопасное определение вызова, а не полную запись фактически подготовленного запроса. `fetchHeader` возвращает скаляр/статус и отбрасывает HTTP-ответ. `HeaderSourceResult` и `VariableSourceResult` содержат только краткие сведения.
- `ResourceForm` и `VariablesForm` выводят `Notice` в начале прокручиваемой формы. `ResourceVariables` использует общий `HTTPSourceFields`; `FileReadContext` защищает незавершённые чтения PEM/proto.
- Одинаковые порты хранилища обслуживают PostgreSQL и YAML. Переносимый `dataset` имеет формат v3, фиксированный перечень коллекций и строгую проверку связей. MCP имеет 45 инструментов, генерируемые схемы и постоянное руководство.
- Действующие dynamic-request-headers/resource-http-variables/environment-http-variables/yaml-data-storage запрещают сохранять тела ответов источников. Их требования меняются явно: журнал хранит только диагностическую копию после маскирования; открытое вычисленное значение доступно исключительно в live-ответе явной проверки.

## Goals / Non-Goals

**Goals:**

- Один источник данных журнала для UI и MCP, одинаковая устойчивость в PostgreSQL/YAML и связь с существующими попытками без изменения их raw JSON.
- Получение фактических параметров в точке подготовки протокольного запроса с маскированием до пересечения границы хранилища.
- Проверка текущего draft использует тот же HTTP/extraction pipeline, что реальный вызов, и сохраняет только диагностический результат.

**Non-Goals:**

- Сетевой packet capture, служебные SQL-запросы самой qag, HTTP-трафик UI/API и отдельные записи для gRPC reflection/соединений транспорта.
- Автоматический повтор запросов, повторный запуск из журнала, изменение ручных статусов или создание прогона при проверке переменной.
- Раскрытие секретных ключей/паролей, автоматическое удаление старых логов, внешний log collector, отдельный экран проверки источников заголовков.

## Decisions

### 1. Отдельные записи журнала и независимые проверки

Добавить модель `CallLog` и порт репозитория для начала/завершения, чтения и фильтрации записей. Каждая запись описывает один прикладной HTTP/gRPC/SQL-вызов либо одно HTTP-обращение источника. Она содержит ID, origin (`editor`, `run`, `variant`, `variable_probe`), stage, порядковый номер внутри операции, время, состояние, `requestSent`, безопасные запрос/ответ и контекст владельца. У записи ровно один владелец: существующая attempt либо новая `HTTPVariableProbe`. `testCaseId/runId/blockId/variantId`, окружение, ресурс и их версии копируются как исторические метаданные при наличии.

`HTTPVariableProbe` хранит ID, scope окружения/ресурса, безопасное определение проверяемого источника и контекста, idempotencyKey/hash, состояния и ссылку на лог. Извлечённого значения в этой модели нет. Новые таблицы и коллекции `callLogs`/`httpVariableProbes` входят в `dataset`, валидатор связей, импорт/экспорт и файловое хранилище.

Ресурс нового draft может ещё не иметь ID: тогда сохраняются environment ID и безопасная подпись владельца. Удаление допустимого несохранённого прогона удаляет принадлежащие ему логи вместе с попытками одной транзакцией, сохраняя прежнюю семантику удаления истории. Остальные записи не удаляются автоматически; закрепление не влияет на их создание. Ссылки переиспользования на чужую попытку не являются обязательными FK: после удаления исходного прогона остаются безопасные сведения `reused`.

Альтернатива — расширить JSON `execution.Result` всем журналом. Отдельная коллекция позволяет искать редакторские попытки и проверки без run ID, не переписывать старые результаты и обновлять этапы независимо.

### 2. Регистрация каждого этапа перед сетью

Сохранённая попытка остаётся корнем обычного выполнения. После подготовки конкретного запроса журнал устойчиво регистрирует его безопасную копию; только затем существующий request gate допускает отправку. Для источника регистрация происходит до его HTTP-запроса, для основного вызова — после получения всех источников. Ошибка регистрации запрещает соответствующее внешнее действие; уже завершённый источник не повторяется.

Фиксация ответа идемпотентна по ID записи; повторяется запись, не сеть. Пока запись не подтверждена, UI/MCP видят `persistencePending`. Выполнение следующего этапа ожидает подтверждения предыдущего, учитывая общий deadline и отмену. Gate и отмена предотвращают начало следующего этапа после подтверждённой отмены; приложение не обещает откат уже отправленного запроса. Сбой процесса оставляет запись `interrupted` с пояснением неизвестного внешнего эффекта. Recovery не отправляет запросы.

У HTTP фиксируются метод, абсолютный URL с query, эффективные заголовки и тело после подстановки/кодирования; у gRPC — endpoint, полный метод, metadata и JSON сообщения; у SQL — адрес без credentials, SQL-текст, режим и упорядоченные типизированные связанные параметры. Это прикладное представление, не байты TLS/HTTP2. Ответы сохраняют прежние типы, коды, headers/trailers, точные числа и SQL NULL. Системные секретные реквизиты подключения в журнал не входят.

Источник `per_run`, взятый из кеша, не создаёт фиктивный HTTP-вызов: существующая диагностика помечает `reused` и при доступности указывает первоначальный log ID. Неотправленный основной запрос показывается как таковой, без выдуманного ответа. Для отказа подготовки доступна причина на уровне попытки/проверки.

Альтернатива — сохранить весь журнал только в конце попытки. Она теряет сведения о завершившемся источнике при аварии во время основного запроса; выбранная регистрация этапов устраняет этот пробел ценой дополнительных записей.

### 3. Раздельные диагностическая и временная проекции

Сборщик удерживает сырой HTTP-ответ источника только в памяти. До записи он добавляет извлечённый скаляр и `prefix + scalar + suffix` в redactor, маскирует известные секреты и JSON/URL/form-экранированные формы, закрывает выбранное JSON-поле в диагностической копии и не сохраняет response cookies/authorization credentials открыто. JSON-числа обрабатываются без float-конверсии. Маскирование применяется также к URL, headers, телу, ошибке, gRPC/SQL-параметрам и всем полям записи.

Если тело источника усечено, не является корректным JSON либо выбранное поле нельзя безопасно обработать, сохраняются статус/headers, безопасная причина и `bodyOmittedReason` вместо сырого тела. Это явная диагностическая неполнота, а не пустой успешный ответ. Для успешного JSON выбранное поле и его отражения скрываются независимо от имени переменной. Тело запроса источника после form-кодирования проходит тот же redactor. Запрет открытых вычисленных значений распространяется на error paths, временные файлы YAML и переносимые записи журнала.

Только live-ответ чтения своей явной проверки содержит `extractedValue` и `formattedValue` с типом исходного скаляра. Поля не добавляются в обычные get ресурса/окружения/попытки, логи, MCP-артефакты или аудит. Для этой выдачи используется отдельный DTO, не сериализуемый в dataset. Ответ помечается `Cache-Control: no-store`.

Значение хранится в ограниченном временном кеше проверки: максимум 128 результатов по 64 KiB извлечённого значения, TTL 10 минут; форматированное значение также ограничено существующей валидацией источника. После истечения/вытеснения/перезапуска метаданные и маскированный лог доступны, но ответ явно содержит `valueUnavailable`; чтение не обращается к источнику. UI очищает показ при изменении draft, закрытии формы и начале новой проверки. Поздний ответ старого draft не заменяет текущий результат. Сохранённые write-only секреты не получают самостоятельного API раскрытия.

Альтернатива — сохранять значение проверки зашифрованным либо создавать MCP-артефакт. Это превращает временный просмотр в отдельное постоянное хранилище чувствительных значений; выбранное исключение ограничено явно запущенной проверкой.

### 4. Проверка источника в контексте draft

Общая сервисная операция поддерживает сохранённую переменную по scope/owner/name и draft выбранной HTTP-переменной. Draft передаёт определение, текущие статические переменные и write-only изменения секретов, необходимые для проверки. Для существующего владельца revision/версия окружения и ресурса проверяются до регистрации, `keep` разрешается сервером из выбранной версии. Новому ресурсу не требуется предварительное сохранение либо корректность несвязанных настроек основного подключения. У источника окружения нет доступа к секретам/переменным ресурса; источник ресурса получает только разрешённый эффективный статический контекст. Другие HTTP-переменные не выполняются.

UI ждёт чтения PEM через существующий FileReadContext, валидирует только проверяемый источник и необходимый контекст и отправляет отдельную команду. Безымянную строку допустимо проверить по выбранному draft; это не создаёт переменную. Обновления конфигурации, новые версии, прогоны и ручные статусы при этом отсутствуют. Сохранение формы по-прежнему чистое и не запускает проверку.

Команда быстро возвращает probe ID и использует отдельный UUID idempotencyKey. Фоновое выполнение использует ограниченные слоты Engine и единый HTTP/extraction код, собственный timeout по умолчанию 30 секунд (до 300), лимиты 5 MiB/64 KiB, без redirects/повторов. Отдельные get/cancel обеспечивают polling и явную отмену. Каждый новый осознанный запуск получает значение заново независимо от fetchMode; он не читает и не наполняет кеш прогонов. Повтор ключа возвращает ту же проверку без сети, в том числе после истечения live-значения.

### 5. Контракты и экраны

Добавить API списка/деталей `/api/v1/call-logs` и `/api/v1/call-logs/{id}`, а также start/get/cancel `/api/v1/http-variable-probes`. MCP получает `qag_call_logs_list`, `qag_call_log_get`, `qag_http_variable_probe_start`, `qag_http_variable_probe_get`, `qag_http_variable_probe_cancel` поверх тех же сервисов. Get проверки возвращает отдельно публичные метаданные и доступную live-проекцию; обёртка MCP не направляет её в общий artifact fallback. Максимальный размер ограниченного результата проверки укладывается в прямой ответ, превышение явно отклоняется без артефакта. Контракты OpenAPI/MCP и TS генерируются обычным `cmd/contract`.

Новый раздел «Журнал вызовов» открывается из навигации и результата конкретной попытки. Список имеет курсор по `(startedAt,id)` от новых к старым, limit 1–100 (по умолчанию 50), фильтры времени, протокола, этапа/origin, состояния, окружения/ресурса, кейса/прогона/попытки. При просмотре запроса/ответа используются общие форматтеры Results, включая JSON, заголовки и SQL-таблицы; ожидания не подменяют фактический ответ. Фильтры работают на сервере без загрузки всех тел; источник виден отдельной строкой со связью с основной попыткой.

На HTTP-строках ResourceVariables появляется «Проверить получение» с состоянием, отменой, локальным результатом и ссылкой на запись журнала. Shared HTTPSourceFields не начинает сеть при редактировании. Нажатие проверки не отправляет submit формы.

Ошибка формы выносится в общую доступную область вне disabled fieldset: в ресурсе — закреплённая область ниже фактических верхних панелей, в модальном окне — область вне прокрутки его содержимого. Сообщение не исчезает по таймеру, доступно с `role=alert`, не перекрывает действия и поля при узком окне/200% масштабе. Рядом с полями сохраняются подробности; из сводки можно перейти к ошибочному полю. На отправке следующего исправленного сохранения сообщение переходит в состояние ожидания, затем заменяется актуальным результатом. Ошибки чтения файлов и проверки источника также получают видимую сводку, не стирая draft.

### 6. Совместимость хранилища и ограничение объёма

Новая миграция после `010_environment_http_variables.sql` добавляет таблицы/индексы журналов и проверок, не изменяя старые миграции. Отдельные индексы обслуживают владельца, время, environment/resource и фильтры протокола/этапа. SQL/FK и файловый валидатор согласуют владельцев и состояния, а удаление прогона удаляет его новые зависимые записи атомарно.

YAML v4 добавляет коллекции журналов и проверок; v1/v2/v3 читаются с пустыми новыми коллекциями. Экспорт создаёт v4 без изменения байтов источника; первая подтверждённая мутация старого YAML обновляет его до v4. Исторические JSON остаются прежними. Совместимое сравнение legacy-defaults продолжается, а одинаковый log/probe ID с другим содержимым отменяет весь импорт.

Для старых попыток без записей журнал строит явно помеченное `legacy` представление из сохранённого request/result, с исходным attempt ID и без фиктивных разрешённых параметров либо источников. Не добавляются новые строки при чтении/миграции, сеть не вызывается. Представление доступно через тот же список/детали; устойчивый синтетический ID отделён от новых UUID и не переносится как новая сущность.

Предел тела диагностического запроса — 1 MiB, ответа — существующие 5 MiB; превышение отмечается отдельно от сетевого результата и не меняет сравнение. Маскирование выполняется до усечения копии. SQL сохраняет прежние 1000 строк. Списки не включают крупные тела. Действующие пределы YAML 256 MiB/100 000 записей сохраняются: при невозможности подтвердить следующую запись приложение возвращает storage/limit error и не начинает очередное внешнее действие. Не вводится скрытый TTL для постоянных логов. README объясняет дополнительный объём и связь удаления логов с удалением несохранённого прогона.

## Risks / Trade-offs

- [Дополнительные устойчивые записи увеличивают задержку и размер YAML] → Разделить summary/details, ограничить диагностические тела и проверить пределы до сети; результат запроса не повторять при отказе записи.
- [Ошибка HTTP-источника может содержать чувствительное тело без извлечённого скаляра] → Сохранять явный пропуск тела, если нельзя безопасно маскировать, с кодом и стадией отказа; тестировать non-2xx, неверный JSON и усечение.
- [Live-значение проверки доступно клиенту, а MCP остаётся открытым по действующей политике] → Ограничить выдачу отдельным явным workflow, памятью/TTL и no-store; не менять согласованную модель доступа MCP и не добавлять публикацию в артефакты/журнал.
- [После аварии неизвестно, успел ли внешний сервис выполнить запрос] → Помечать interrupted/неопределённость, сохранять подтверждённые этапы, не обещать полный wire trace и не возобновлять сеть.
- [Старые попытки не содержат фактических параметров и тел источников] → Показывать legacy-детали с отметкой неполноты, не реконструировать их по текущим ресурсам.
- [Закреплённые панели могут перекрывать друг друга] → Использовать фактические размеры/scroll container, проверить оба modal/page контекста, обе темы, клавиатуру и узкий viewport.

## Migration Plan

1. Добавить новые модели, миграцию и чтение v1–v4; обновить полный перенос и восстановление до включения журналирования в Engine.
2. Подключить маскирующий сборщик и probes, затем общие API/MCP/контракты и UI. Проверить PostgreSQL и YAML на одинаковых сценариях, включая отказ записи, отмену и перезапуск.
3. Выполнить перенос PostgreSQL → YAML → PostgreSQL с логами и метаданными проверок, убедившись, что live-значений нет в файле и истории.
4. Перед обновлением рекомендовать обычный полный backup. Для отката остановить приложение и восстановить предыдущую версию бинарника вместе с согласованным backup до v4; старый бинарник не открывает новый YAML. Деструктивная обратная миграция автоматически не выполняется.
