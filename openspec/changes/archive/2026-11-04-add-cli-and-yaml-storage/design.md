## Context

Мотивация и согласованный объём — в [proposal.md](proposal.md). Прочитаны текущие runtime/storage/repositories, demo, отчёты, сборка и соответствующие основные спецификации. Наблюдаемое состояние:

- `go.mod` объявляет `module qag`; Go-пакеты импортируют `qag/...`. Установочный путь публичного репозитория должен стать путём модуля.
- `web/assets.go` встраивает `web/dist`, исключённый из Git. `scripts/build.ps1` и Dockerfile предварительно собирают Vite; `go install ...@version` не выполняет эти действия.
- `cmd/qag/main.go` поддерживает только сервер и `healthcheck`, требует два DSN и 32-байтовый ключ. Startup открывает PostgreSQL, берёт advisory lock, применяет восемь миграций, подготавливает demo, восстанавливает прерванные операции, запускает один Engine и общие UI/MCP.
- Репозитории `catalog`, `resources`, `runs` содержат SQL и принимают `*pgxpool.Pool`. Engine, HTTP API и reporting зависят от конкретных указателей репозиториев. Одного нового параметра конфигурации для YAML недостаточно.
- Публичные модели не являются полным backup: они скрывают секреты, request hashes и некоторые связи/версии. В ресурсах используется AES-GCM с associated data из ID сущности/версии. Отчёты читают согласованный снимок и неизменяемые изображения.
- Demo HTTP/gRPC напрямую читают PostgreSQL; `StartRun` заранее разрешает и проверяет ресурсы всех блоков. Простое удаление demo SQL-ресурса запретило бы запуск всего примера.
- Пользователь выбрал запуск Web UI/MCP и команды переноса из CLI, объединение по ID с полным отказом при различиях и перенос всех секретов. Уточнение: SQL-шаг примера в YAML остаётся запускаемым и ошибается при вызове.

Основные спецификации требуют PostgreSQL для всего хранения, изображений и demo и запрещают обратную выдачу ключа. Delta-файлы явно меняют эти требования: PostgreSQL остаётся прежним backend, YAML становится альтернативой; только локальные файлы полного переноса получают открытые секреты. Защита браузерного API и открытый по умолчанию MCP сохраняются.

## Goals / Non-Goals

**Goals:**

- Один устанавливаемый бинарник с готовым UI и тем же Engine/отчётами для обоих backend.
- Общие предметные контракты и переносимый граф данных с сохранением ID и фактов истории.
- Файловая транзакция подтверждается до внешнего действия; импорт фиксируется целиком или отклоняется.
- Прежние PostgreSQL/Compose-параметры продолжают выбирать БД без переноса или ротации реквизитов.

**Non-Goals:**

- CRUD/исполнение всех предметных операций отдельными CLI-командами, TUI, фоновые службы и автооткрытие браузера.
- Синхронизация нескольких работающих установок, импорт с заменой конфликтов, автоматическое переназначение ID или live reload файла.
- SQLite, встроенный PostgreSQL, SQL-эмулятор и обязательный контейнер для YAML-режима.
- Объединение настроек установки/ролей PostgreSQL с данными qag; раздача полного YAML с секретами через UI/MCP.

## Decisions

### 1. Публичный Go-модуль и подготовленные assets в поставке

Изменить путь модуля на `github.com/SardelkaS/qag` и все Go-imports, включая генераторы, примеры и тесты. Установочная команда — `go install github.com/SardelkaS/qag/cmd/qag@latest`, с возможностью закрепить опубликованную версию. Корневой main-пакет не добавляется: существующий `cmd/qag` уже даёт имя бинарника `qag`.

Ввести отслеживаемое дерево `web/bundle` с готовым Vite UI, favicon, изображениями, шрифтами/OFL и manifest хешей. `web.Assets()` встраивает это дерево. Сборка разработчика сначала формирует `web/dist`, затем детерминированно обновляет bundle; проверка сравнивает новое дерево с поставляемым. Go module archive должен включать bundle без Node и без build hooks. Docker продолжает собирать UI из исходников и обновляет bundle внутри build-stage тем же механизмом. Для Windows включить подготовленные `.syso` иконки поддерживаемых архитектур в модуль, изменив соответствующее исключение Git; иначе установка через Go потеряет PE-иконку, требуемую существующей спецификацией.

Альтернативы: `go generate` при установке не запускается; загрузка UI при первом старте добавляет сеть и несовместимость версий; HTML-заглушка нарушает требование готового приложения. Отслеживаемый bundle увеличивает репозиторий, зато делает установку самостоятельной. До публикации проверять установку из сформированного module zip через изолированный локальный Go proxy; после публикации дополнительно доступна обычная удалённая команда. Apply сам по себе не публикует коммит или тег.

### 2. Небольшой CLI поверх общего runtime

Выделить разбор команд из `main` в тестируемый слой, используя стандартный `flag.FlagSet`. Сначала разобрать команду и флаги, затем загружать выбранный runtime: help/version и ошибки синтаксиса не касаются данных. Версию установленного модуля читать через `runtime/debug.ReadBuildInfo`, сохранив обозначение dev для локальной сборки.

Команды и примеры целевого интерфейса:

```console
qag
qag serve --data-file ./workspace.yaml
qag serve --storage postgres --database-url <dsn> --demo-database-url <reader-dsn>
qag data export --storage postgres --output ./backup.yaml
qag data import --storage postgres --input ./backup.yaml --dry-run
qag data import --storage postgres --input ./backup.yaml
qag data import --data-file ./other.yaml --input ./backup.yaml
qag healthcheck
qag --help
qag --version
```

В примерах DSN условные; документация также показывает передачу секретов через env/приватный config. Параметры выбранного хранилища применяются к serve/export/import. `--input`/`--output` — отдельные переносимые документы, `--data-file` — рабочее YAML-хранилище. Запуск с `--data-file` не импортирует данные в параллельно настроенную БД. Команды переноса не требуют слушателей, demo-DSN, браузерной сессии или Engine; для PostgreSQL им нужны подключение, выбранное пространство и ключ секретов.

Результаты CLI: 0 — успех, 2 — ошибочная команда/конфигурация, 1 — ошибка хранения/переноса или конфликт. В stderr — безопасная диагностика, в stdout — адреса либо счётчики. Значения DSN, ключей, секретов и целый YAML не печатаются. В README остаётся порядок предварительной подготовки отдельной demo-роли PostgreSQL; обычный serve её не создаёт с административными привилегиями.

Альтернатива — отдельный клиент всех MCP-инструментов — не соответствует выбранному пользователем объёму и дублирует существующий интерфейс автоматизации.

### 3. Выбор backend без скрытого перехода

Разрешение значений: явно переданные флаги → env → `QAG_CONFIG_FILE`/`--config` → defaults. Файл конфигурации остаётся приватным JSON установки и не смешивается с файлом данных. Невалидный явно выбранный config всегда даёт ошибку; подключения неиспользуемого backend не валидируются и не открываются.

- `--storage` либо `QAG_STORAGE` явно выбирает `postgres`/`yaml`.
- Без явного режима `--data-file` выбирает YAML, `--database-url` — PostgreSQL; совместная передача этих двух флагов запрещена.
- Затем учитываются эффективные `QAG_DATA_FILE` и `QAG_DATABASE_URL`: одно значение выбирает режим, оба без явного режима дают ошибку. Отсутствие обоих выбирает YAML `./qag.yaml`.
- Явный `--storage yaml` позволяет оставить старые PostgreSQL-env, но не принимает явно переданный DB-флаг; зеркально для postgres и файлового флага. Низкоприоритетные настройки другого backend игнорируются.
- Явно выбранный postgres требует прежних реквизитов для serve; отказ никогда не создаёт YAML. Compose с прежним `QAG_DATABASE_URL` остаётся PostgreSQL-установкой.
- Проверки namespace/test mode PostgreSQL остаются прежними; файловые тесты используют отдельные временные каталоги. `--address` сохраняет native loopback/container-ограничения.

### 4. Интерфейсы репозиториев и один движок

Ввести предметные интерфейсы каталог/ресурсы/прогоны в нейтральном `internal/ports`, с текущими моделями и сигнатурами нужных операций. Потребители Engine, HTTP API, MCP и reporting получают интерфейсы. Существующие PostgreSQL-репозитории реализуют их без переписывания SQL. Для demo и runtime отдельно определить доступ к записи/подготовке системных данных, health, владению и закрытию backend.

`internal/filestore` предоставляет три реализации поверх одного состояния и одного координатора файловой транзакции. Общие чистые правила именования, черновиков, revision, оценки, retention, формирования отчёта и публичного маскирования выделяются из PostgreSQL-реализаций и используются обеими. Операции, сейчас атомарные в SQL, должны оставаться атомарными и здесь: начало прогона с его шагами/очередью, регистрация попытки/идемпотентность, смена версии, PassAll, отмена/завершение, закрепление первого результата, отчётный снимок.

Внешние вызовы остаются в одном Engine/Runner; файл не получает второго планировщика. Жизненный цикл backend возвращает потерю владения как прежде PostgreSQL instance lock. MCP использует текущие 43 инструмента; новых инструментов файлового импорта/экспорта не требуется, поскольку это локальные эксплуатационные команды.

Альтернативы: имитация SQL в памяти либо запуск временной PostgreSQL нарушают самостоятельность YAML. Перенос всех PostgreSQL-операций на новый универсальный ORM увеличил бы риск действующей установки без пользы для пользовательского поведения.

### 5. Один переносимый документ, отдельный от публичных DTO

Добавить `internal/dataset` с versioned документом `format: qag`, `version: 1`, `data: ...`. Он описывает устойчивые записи и связи, а не только UI-проекции. Группы соответствуют фактам хранения:

| Группа | Содержимое |
|---|---|
| Каталог | folders, testCases, точные определения/архив/даты/revision |
| Ресурсы | environments, environmentVersions, resources, resourceVersions, указатели текущих версий |
| Прогоны | runs, runSteps, runResourceVersions, снимки, retention и ключи/хеши команд |
| Исполнение | callAttempts, runCallVariants, variantVersions, runBatches, batchItems |
| Дополнения | expectedImages с байтами, builtinDemo со связями, demoItems |

`schema_migrations`, роли и установки остаются инфраструктурой назначения. Секреты находятся в отдельных `secrets`-картах версий, а не в публичных снимках/результатах. Изображения содержат base64 и метаданные/SHA-256; PEM и proto files уже являются строками в конфигурациях и переносятся содержимым. Для сохранённых JSON-снимков/запросов/результатов использовать точное raw JSON-представление в YAML literal string, не промежуточный `map[string]any` с float64. Это сохраняет legacy-поля и точные числовые токены. Текущие предметные операции создают новые значения по действующим моделям, не переписывая старые записи.

Типизированный YAML-кодек проверяет неизвестные поля, дубликаты ключей и запрещённые aliases/tags до DTO, затем целостность графа. Использовать Go YAML-парсер с доступом к узлам и строгим decoding, закрепив зависимость в модуле. Лимиты: 256 MiB encoded-файла, 64 уровня, 100 000 записей группы, плюс действующие лимиты изображения/proto/ответов. Валидатор различает допустимый черновик/legacy-историю и готовность к исполнению; не вызывать нормализацию, которая назначит новые ID или перепишет snapshot.

Каноническое сравнение сортирует ключи, коллекции по обычным/составным ID, UTC-представление дат и объявленные множества; значимый порядок шагов, заголовков, SQL-столбцов/строк и вариантов сохраняется. JSON сравнивается без float и без потери значимых числовых представлений; секреты — по расшифрованным значениям. Служебные метаданные экспорта не участвуют в равенстве. Формат и пример без реальных секретов описать отдельно и связать из README.

### 6. Файловые транзакции и владение

Файл загружается один раз под эксклюзивным владением. Чтение использует согласованный неизменяемый снимок; мутация сериализуется mutex, строит независимый кандидат, проверяет предметные ограничения и полностью кодирует его. Фиксация: приватный temp в том же каталоге → запись/flush/sync → атомарная замена → необходимое платформенное подтверждение метаданных → публикация нового снимка. Прямое truncate/rewrite рабочего YAML запрещено. Если ошибка до замены — кандидат отбрасывается. Если исход замены/подтверждения неизвестен — backend отмечается неисправным, не выдаёт ложный успех и не допускает новые внешние действия до повторного открытия/согласования.

Использовать платформенные операции Windows и POSIX с тестами отказов на границах. Постоянный `<data-file>.lock` держит блокировку ОС и не заменяется вместе с данными; обычное существование lock-файла не означает занятость. Канонизировать путь, отклонять неподдерживаемые алиасы файлов, чтобы один файл нельзя было открыть как два независимых backend. Для экспорта новый output резервируется без перезаписи; два export не могут одновременно занять одно имя. До записи рабочего файла проверять его поколение/хеш для обнаружения внешнего редактирования. Условие работы — локальная файловая система с поддержкой нужной блокировки/атомарной замены; сетевые папки и одновременное ручное редактирование не поддерживаются.

Создаваемые YAML/temp/lock — private: POSIX 0600, Windows ACL текущего пользователя, без наследования общего чтения для содержимого. Служебные lock-файлы не содержат секретов. Не включать реальные YAML в Git; добавить точечное исключение default `qag.yaml` и его рабочих файлов. Файл не требует соседней БД или ключа; lock/temp — служебные артефакты и не нужны для переноса.

Альтернатива append-only journal ускорила бы большие состояния, но потребовала бы второго файла данных и отдельного восстановления. В первой реализации принят полный rewrite ограниченного документа; лимит и стоимость явно документируются.

### 7. Перенос под тем же эксклюзивным владением

`internal/datatransfer` работает с backend snapshot/import-портами. Export берёт тот же instance lock, что serve, проверяет совместимость пространства/формата и читает все группы в PostgreSQL repeatable-read snapshot либо YAML-снимке. Он не вызывает bootstrap/recover и не изменяет источник. Команда требует остановить использующий хранилище сервер; это сознательно упрощает согласованность. Старые running/queued записи допускаются и переносятся буквально.

Import:

1. Прочитать и проверить весь вход; не запускать listeners, Runner или источники заголовков.
2. Получить эксклюзивное владение назначением и прочитать текущий граф. Для нового YAML использовать пустой граф без записи; для нового PostgreSQL dry-run проверяет совместимость/права без DDL.
3. Объединить записи по ID/составным ключам, сравнив полное предметное содержимое. Одинаковые пропустить, новые добавить. Проверить весь итоговый граф и уникальности, включая normalized names, owner/revision, idempotencyKey, first_run/first_success, единственность builtinDemo.
4. Любой конфликт даёт тип/ID и безопасную причину без old/new содержимого. `--dry-run` завершает работу здесь и ничего не создаёт.
5. Для реального импорта в новое PostgreSQL-пространство подготовить штатную схему неизменёнными миграциями, не создавая системный пример. Предварительная проверка не делает такую подготовку успешным импортом: пользовательские записи фиксируются только одной транзакцией после повторной проверки под владением. В подготовленном пространстве вставить записи в порядке зависимостей с deferred constraints, зашифровав секреты ключом назначения. В YAML сохранить объединённый кандидат одной файловой транзакцией.

Экспорт читает внутренние версии секретов через Vault с associated data ID; импорт seal использует те же ID и ключ назначения. Так разные ciphertext не создают ложные конфликты. Исходный ключ не экспортируется. После импортированного незавершённого состояния только будущий serve вызывает обычный Recover, без сетевого replay.

Из-за строгого объединения обновлённый объект с тем же ID — конфликт даже при большей revision. Независимые установки могут конфликтовать по системной singleton-связи или именам с разными ID; указать перенос в новое назначение как путь сохранения исходных ID, не скрывать это ограничение. Повтор успешного импорта до запуска/изменений назначения должен быть полным no-op. Source и target не должны обозначать один физический файл.

### 8. Demo без PostgreSQL и явная ошибка SQL

Выделить чтение `demo.Item`/готовности и подготовку системных данных из прямого доступа к pool. PostgreSQL-адаптер сохраняет qag_demo и отдельную ограниченную роль. YAML-адаптер читает `demoItems` из общего документа, обеспечивает тот же HTTP/gRPC-контракт и reflection.

Системный SQL-ресурс остаётся с прежним ID и kind `postgresql`. Добавить внутренний признак недоступности конкретной версии системного ресурса с безопасной публичной причиной. Только bootstrap может его установить; пользовательская конфигурация не получает способ обхода обычной валидации ресурсов. Freeze/Resolve и проверка прогона допускают такой системный placeholder без DSN, не удаляя SQL-блок. При выполнении сначала устойчиво зарегистрировать попытку, затем завершить её `error` с кодом `demo_sql_unavailable`, не вызывая PostgreSQL Runner. Исследовательская SQL-попытка у этого блока ошибается так же. Очередь продолжает оставшиеся блоки; итог исходного вызова учитывается как обычная ошибка.

Признак фиксируется в версии/контексте, а не вычисляется заново из текущего глобального режима при чтении истории. UI ресурсов и пример показывают понятную причину. При необходимости добавить необязательное публичное поле доступности с обновлением OpenAPI/MCP schemas/TypeScript, не менять имена инструментов. Readiness YAML проверяет документ и HTTP/gRPC; отсутствие demo-БД не считается отказом приложения.

После переноса bootstrap сохраняет импортированные системные ID и создаёт новую текущую версию системных подключений под новый режим/адрес. Старые версии/снимки/ошибки не меняются. Пользовательские SQL-запросы и адреса не переписываются. Для корректного SQL после импорта в PostgreSQL требуется отдельно подготовленная demo-роль назначения. Изолированные тестовые схемы могут потребовать новой версии системного сценария с текущим namespace для новых прогонов; старые снимки остаются исходными.

Альтернативы удаления SQL-шагов и блокировки всего примера не соответствуют уточнению пользователя. Заведомо неверный сетевой DSN дал бы случайный эффект и ненужную задержку; явная зарегистрированная ошибка показывает причину сразу.

### 9. Проверки на уровне общих контрактов и поставки

Параметризовать существенные проверки репозиториев/Engine для PostgreSQL и YAML: revision/readOnly/архив, русский алфавит и tie-break, транзакции, retention, версии ресурсов/маскирование, изображения истории, очередь/отмена, варианты, отчёт, идемпотентность и восстановление. PostgreSQL продолжает использовать существующие fixture/manifest/ограниченные роли одной БД; YAML — отдельный tmp-каталог. Failpoints файловой записи и реальные дочерние процессы проверяют crash/reopen, блокировку и запрет сети без фиксации.

Проверить все 43 MCP-инструмента в YAML-режиме и UI-путь с сохранением, прогоном и отчётом; выполнить реальные HTTP/gRPC и пользовательский SQL к изолированной целевой PostgreSQL. Отдельно полный круг PostgreSQL → YAML → PostgreSQL с разными мастер-ключами, конфликтом в последней записи, старым изображением/секретом, legacy-данными и running/queued без replay.

Установку проверять вне checkout с чистыми Go caches/GOBIN, опубликованной либо тестовой module-proxy версией, без Node/Docker в PATH. Запускать бинарник из другого каталога, проверять embedded UI/favicon/fonts и серверный PDF. Windows/Linux/macOS должны собираться; платформенные права/lock/replace проверяются на соответствующей ОС. Существующий Compose/PostgreSQL smoke и проверки checksum восьми миграций остаются обязательными.

## Risks / Trade-offs

- [Повторная реализация транзакционных правил] → Общие чистые функции и одинаковые контрактные сценарии обоих backend, без второго Engine.
- [Большие изображения/история увеличивают полную YAML-перезапись и память] → Лимиты до декодирования/фиксации, явный отказ вместо усечения, рекомендация PostgreSQL для большого состояния.
- [YAML содержит открытые секреты] → Это явная часть переносимого формата; приватные права всех файлов, отсутствие дампа в консоль/API и заметное описание в CLI/README. Мастер-ключ PostgreSQL по-прежнему вне БД и YAML.
- [Частичное подтверждение замены файла] → Платформенная фиксация, failpoints, состояние ошибки backend и запрет внешнего запуска до восстановления.
- [Независимые состояния нельзя автоматически объединить без конфликтов] → Подробные безопасные ID/причины, dry-run, перенос в новое назначение; без скрытого overwrite/remap.
- [Bundle или PE-иконка отстали от исходников] → Детерминированная подготовка, проверка manifest/свежести и установка из module zip, не использующая локальный web/dist.
- [Смена Go module path затрагивает генераторы и тесты] → Атомарное обновление imports и прогон сборки/контрактов всех команд, без изменения wire-данных.

## Migration Plan

1. Добавить интерфейсы и перенести потребителей, оставив PostgreSQL поведением по прежней конфигурации; проверить существующие данные без изменения миграций 001–008.
2. Добавить dataset/YAML/transfer и параметризованные проверки, затем подключить выбор backend и консольные команды.
3. Подготовить поставляемые assets, новый module path, документацию и проверки установки. Публикация коммита/тега выполняется отдельным действием пользователя.
4. Существующую установку обновлять с прежними DSN/ключом и томами. Для перехода остановить qag, экспортировать в новый приватный YAML, затем запустить `qag serve --data-file <path>`. БД и её конфигурация не удаляются.
5. Для обратного переноса импортировать в целевую PostgreSQL под её ключом и с правилом строгого объединения; предпочтительно в новое пространство при расхождении истории. Подготовить отдельную demo-роль и запустить сервер.
6. Откат к прежнему бинарнику возможен на сохранённой PostgreSQL с исходным ключом: старые миграции и формат её записей не заменяются. Новые данные YAML сначала перенести новым CLI; старый бинарник YAML не читает. Не выполнять автоматическую замену рабочей БД ради отката.
