## MODIFIED Requirements

### Requirement: Локальный Web UI на Go и TypeScript

Приложение SHALL предоставлять браузерный UI на TypeScript и сервер на Go без формы входа для одного пользователя. Готовая сборка SHALL обслуживать UI, API и включённый по умолчанию MCP одним Go-процессом на общем HTTP-адресе. Нативный режим MUST слушать только loopback-интерфейс. Явно выбранный контейнерный режим SHALL разрешать listener, доступный перенаправлению Docker, при публикации HTTP только на loopback хоста в штатном Compose. Исполнение целевых HTTP-, gRPC- и SQL-вызовов SHALL происходить на сервере. Изменяющие состояние и исполняющие команды браузерного API MUST не приниматься из постороннего веб-источника; настройка контейнерного режима MUST не отключать его проверку Host и Origin. Браузерный API MUST сохранять CSRF-защиту, а MCP SHALL быть доступен без авторизации, браузерной сессии и ограничений Host/Origin/cross-site. Оба канала SHALL использовать один жизненный цикл и те же данные без второго владельца выбранного хранилища. Выбор PostgreSQL либо YAML SHALL одинаково применяться к UI, API и MCP, не меняя правил доступа.

#### Scenario: Запуск и открытие UI
- **WHEN** пользователь запускает настроенное приложение и открывает его локальный адрес
- **THEN** появляется каталог тест-кейсов без страницы входа и доступен выбор раздела ресурсов

#### Scenario: Команда с постороннего сайта
- **WHEN** другая веб-страница пытается отправить команду запуска через браузерный API локального сервера приложения
- **THEN** сервер отклоняет её до выполнения внешнего запроса

#### Scenario: Контейнерный и нативный listener
- **WHEN** приложение настроено слушать все контейнерные интерфейсы
- **THEN** запуск разрешён только при явном контейнерном режиме, а нативная конфигурация по умолчанию сохраняет запрет такого listener

#### Scenario: Одновременная работа UI и MCP
- **WHEN** настроенный MCP-клиент сохраняет сценарий и пользователь открывает его в UI
- **THEN** оба канала видят те же данные, а подключение MCP не запускает повторное восстановление прогонов

#### Scenario: Раздельная защита команд
- **WHEN** MCP обращается без авторизации, а запрос к браузерному API не содержит CSRF
- **THEN** MCP-команда доступна, но изменяющая браузерная команда отклоняется по прежним правилам

#### Scenario: Общий YAML для UI и MCP
- **WHEN** приложение запущено с YAML и MCP меняет пользовательский кейс
- **THEN** браузер видит тот же кейс и revision без второго файлового состояния или PostgreSQL

### Requirement: Постоянное хранилище приложения

Приложение SHALL хранить папки, сценарии, окружения, версии ресурсов, секреты, изображения, прогоны, статусы, комментарии, очереди, исследовательские варианты и подтверждённые результаты в явно выбранном PostgreSQL- либо YAML-хранилище. Перезапуск приложения либо браузера MUST не терять успешно записанные данные. PostgreSQL-установка SHALL использовать одну физическую БД с рабочими и изолированными тестовыми схемами. YAML-установка SHALL работать с одним выбранным файлом без служебной БД. Подключения, роли и пространства данных приложения и SQL-ресурсов SHALL задаваться явно, а исполнение блока MUST не использовать служебное подключение приложения по умолчанию. Встроенный SQL в YAML-режиме SHALL оставаться запускаемым и возвращать явную ошибку отсутствующей demo-БД при выполнении; остальные блоки примера MUST не блокироваться этим отсутствием.

#### Scenario: Данные после перезапуска
- **WHEN** пользователь сохранил тест-кейс, ресурс и прогон, затем перезапустил Go-процесс
- **THEN** каталог, настройки и сохранённая история загружаются из выбранного хранилища в прежнем состоянии

#### Scenario: SQL-блок без целевого ресурса
- **WHEN** пользовательский SQL-блок не имеет доступного PostgreSQL-ресурса в выбранном окружении
- **THEN** запуск завершается ошибкой подготовки, а запрос не отправляется в служебные таблицы приложения

#### Scenario: Тестовые и рабочие данные
- **WHEN** основной qag и тестовый экземпляр подключены к одной физической БД
- **THEN** каждый работает в своём пространстве схем и тестовые подключения не получают доступ к рабочему каталогу

#### Scenario: Файловое хранение без БД
- **WHEN** qag запускается с YAML и без подключений PostgreSQL
- **THEN** каталог, окружения, изображения, прогоны и история доступны, а пользовательские SQL-ресурсы могут обращаться к внешней PostgreSQL

### Requirement: Контролируемый запуск и миграции

При запуске приложение SHALL проверять конфигурацию и выбранное хранилище. В PostgreSQL-режиме SHALL проверяться подключение, разрешённые схемы и поддерживаемая версия, применяться версионированные миграции только к своему пространству данных и подготавливаться demo-схема и ограниченная SQL-учётная запись. В YAML-режиме SHALL проверяться формат, версия и связи документа без подключения к PostgreSQL и её миграций. До готовности SHALL быть подготовлены системный пример и ресурсы выбранного режима, а также запущены демонстрационные HTTP/gRPC. Отсутствие demo-БД в YAML-режиме MUST не препятствовать готовности. Некорректная конфигурация, несовместимое либо недоступное выбранное хранилище MUST приводить к понятной диагностике без ложной готовности и без переключения backend. Тестовый PostgreSQL-запуск MUST не подставлять рабочие схемы при отсутствии явной конфигурации. Пароли и ключ шифрования MUST не включаться в сообщения ошибки. Контейнерная PostgreSQL-установка SHALL ожидать успешную подготовку постоянной конфигурации, готовность PostgreSQL и подготовку ограниченной demo-роли; повторная подготовка MUST не менять исходные реквизиты.

#### Scenario: Первый запуск на пустой БД
- **WHEN** приложение запущено с корректным подключением к пустой выделенной PostgreSQL-БД
- **THEN** своё пространство создаётся миграциями, демонстрационный сервис и пример подготовлены, а интерфейс открывается с закреплённым примером и пустым пользовательским каталогом

#### Scenario: Недоступная БД при запуске
- **WHEN** PostgreSQL не отвечает либо аутентификация приложения не проходит
- **THEN** запуск сообщает безопасную причину и не открывает рабочий UI как успешно готовый

#### Scenario: Тестовый bootstrap
- **WHEN** тестовый экземпляр запускается в своих схемах общей БД
- **THEN** он подготавливает собственный пример и не меняет ID, ресурсы или историю рабочего примера

#### Scenario: Ошибка контейнерной подготовки
- **WHEN** подготовительный контейнер не смог сохранить конфигурацию или подготовить demo-роль
- **THEN** qag не объявляется healthy и не начинает внешние вызовы, а причина доступна без секретных значений

#### Scenario: Готовность файловой установки
- **WHEN** YAML валиден и доступен, а PostgreSQL не установлена
- **THEN** UI, MCP и demo HTTP/gRPC объявляются готовыми без попытки подключения к служебной БД

### Requirement: Устойчивость записи при работе

Система SHALL атомарно сохранять связанные изменения и SHALL не сообщать об успешном сохранении до подтверждения выбранного хранилища. При недоступном хранилище введённый текст MUST оставаться в редакторе, а запуск нового внешнего вызова MUST быть запрещён, если не удалось устойчиво записать его начало. Потеря записи после уже отправленного вызова SHALL показываться как неопределённый результат без автоматического повторного исполнения.

#### Scenario: Ошибка сохранения сценария
- **WHEN** выбранное хранилище становится недоступно во время сохранения
- **THEN** UI показывает ошибку и сохраняет несохранённые правки пользователя для повторной попытки

#### Scenario: Нельзя записать начало вызова
- **WHEN** пользователь нажимает запуск, но сервер не может устойчиво сохранить начало попытки в выбранном хранилище
- **THEN** внешний ресурс не вызывается, а пользователь видит ошибку хранения

#### Scenario: Ошибка файловой фиксации
- **WHEN** YAML нельзя устойчиво обновить перед отправкой нового вызова
- **THEN** вызов и источник заголовка не выполняются, UI сохраняет несохранённый ввод, а MCP получает ошибку хранения

### Requirement: Инструкция локального развёртывания

Репозиторий SHALL содержать воспроизводимые инструкции сборки Go/TypeScript с иконкой, запуска одной PostgreSQL, подготовки изолированных тестовых схем/ролей, настройки подключения и ключа секретов, запуска приложения и выполнения проверок. README SHALL начинаться с актуального контейнерного запуска приложения и БД через Docker Compose, отдельно описывать эквивалентный запуск через Makefile и доступный адрес браузера. Для контейнерного пути SHALL быть достаточны Docker и Compose; GNU Make SHALL требоваться только для Make-варианта. Документация SHALL объяснять смену опубликованного порта, сохранение данных и ключа, импорт прежней установки и адреса ресурсов хоста при выполнении запросов из контейнера. Нативный Windows-режим SHALL оставаться описанным для разработки; его команды MUST работать в PowerShell. Документация SHALL описывать backup PostgreSQL и отдельного ключа/конфигурации, переход со старого тестового контейнера без удаления рабочего тома, ограничения локального режима и отсутствие гарантии отката внешнего действия при отмене. Платформенные возможности экспорта SHALL описываться согласно фактическому backend: Linux использует browser HTML clipboard, native Windows clipboard относится к нативному Windows-запуску. README SHALL описывать автоматическое включение MCP без токена, адрес /mcp на обычном и изменённом порту, совместимые протоколы, подключение без Authorization, каталог инструментов и полный пример от встроенного кейса до отчёта. Инструкция SHALL различать серверные файлы и clipboard клиента, объяснять revision, idempotencyKey, истечение артефактов и ограничения локального доступа без публикации реальных секретов. README SHALL дополнительно описывать самостоятельную установку через go install, PATH/версию Go, CLI-справку, запуск с YAML-файлом либо PostgreSQL, приоритет флагов/env/config и команды полного экспорта/импорта с dry-run. Документация SHALL объяснять открытые секреты и приватные права YAML, необходимость остановить владельца перед переносом, конфликты объединения, запуск SQL-примера без БД с явной ошибкой и независимость пользовательских SQL-ресурсов. YAML-перенос MUST отличаться от PostgreSQL dump/restore и от экспорта отчёта.

#### Scenario: Настройка на чистой машине
- **WHEN** разработчик следует инструкции с установленными указанными инструментами и чистой PostgreSQL-БД
- **THEN** он собирает контейнерный образ, запускает UI и проходит демонстрационный ручной тест-кейс с локальными тестовыми ресурсами

#### Scenario: Проверки на общей БД
- **WHEN** разработчик выполняет документированные проверки рядом с рабочим приложением
- **THEN** используется один PostgreSQL-контейнер, тестовые объекты изолированы схемами и рабочие данные сохраняются

#### Scenario: Два способа контейнерного запуска
- **WHEN** пользователь выбирает в README прямой Docker Compose либо вариант с GNU Make
- **THEN** оба варианта приводят к одному адресу Web UI и одному сохраняемому состоянию без требования установить Go или Node.js на хост

#### Scenario: Подключение MCP по README
- **WHEN** пользователь следует MCP-разделу README для штатного Compose либо нативной разработки
- **THEN** клиент подключается по документированному адресу, получает инструменты и проходит встроенный пример с готовым отчётом без обязательного браузера

#### Scenario: Самостоятельный запуск по README
- **WHEN** пользователь с установленным Go следует инструкции go install и запуска с YAML
- **THEN** готовые UI и MCP работают без Node.js, Docker, PostgreSQL и файлов репозитория

### Requirement: Повторяемый жизненный цикл встроенного сервиса

Демонстрационные интерфейсы SHALL запускаться и завершаться вместе с процессом qag. В нативном режиме их слушатели MUST принимать соединения только через loopback. В контейнерном режиме демонстрационный HTTP SHALL использовать общий опубликованный локальный HTTP-порт qag, а gRPC SHALL оставаться на loopback внутри контейнера. Системные ресурсы SHALL использовать адреса, достижимые исполнителю запросов, а не wildcard-адрес listener. Занятый порт, недоступное выбранное хранилище демонстрационной записи либо, в PostgreSQL-режиме, некорректная отдельная SQL-учётная запись SHALL давать безопасную диагностику без ложной готовности. Повторный запуск SHALL сохранять идентичность встроенного кейса, окружения и истории и MUST не создавать повторные закреплённые элементы. Завершение приложения SHALL освобождать демонстрационные слушатели и подключения. В YAML-режиме демонстрационные HTTP/gRPC SHALL читать тот же файловый набор данных; заведомое отсутствие демонстрационной PostgreSQL SHALL отражаться только ошибкой SQL-попытки, без остановки сервера или ложного SQL-успеха.

#### Scenario: Повторный запуск с историей примера
- **WHEN** пользователь завершил прогон встроенного кейса и перезапустил qag
- **THEN** кейс и сохранённая история имеют прежние идентификаторы, а в каталоге остаётся один закреплённый пункт

#### Scenario: Занят демонстрационный gRPC-порт
- **WHEN** заданный локальный gRPC-адрес занят другим процессом
- **THEN** qag сообщает о недоступном демонстрационном порте, не показывает готовность и освобождает уже созданные им слушатели

#### Scenario: Завершение и повторный запуск
- **WHEN** процесс qag штатно завершён, а затем запущен с прежними адресами
- **THEN** демонстрационные HTTP/gRPC снова доступны без оставшегося отдельного тестового процесса

#### Scenario: Внутренний адрес HTTP-примера
- **WHEN** HTTP-listener qag слушает все интерфейсы внутри контейнера
- **THEN** системный HTTP-ресурс указывает на достижимый локальный адрес внутри этого контейнера, а выполнение примера не обращается к wildcard-адресу

#### Scenario: Отказ SQL не останавливает YAML-сервер
- **WHEN** в YAML-режиме выполнен встроенный SQL-блок без demo-БД
- **THEN** попытка сохранена с явной ошибкой, а UI, MCP, HTTP/gRPC и readiness продолжают работать

### Requirement: Совместимое обновление и резервное копирование новых данных

Обновление SHALL сохранять существующие кейсы, окружения, переменные, секреты, TLS/mTLS-конфигурации, встроенный пример, прежние ручные статусы и историю. Старые записи SHALL получать совместимые значения новых необязательных полей без переписывания снимков. PostgreSQL-backup SHALL включать изображения, описания окружений, варианты, версии их запросов и данные очередей вместе с историей. Восстановление с исходным ключом SHALL позволять читать эталоны и использовать прежние секреты. Полученные заголовки MUST не становиться открытыми данными backup. Восстановленный незавершённый прогон MUST не возобновлять внешние действия автоматически. Добавление YAML-backend MUST не менять прежний мастер-ключ PostgreSQL, ID и применённые SQL-миграции. Перенос через YAML SHALL сохранять тот же граф данных по правилам portable-data-transfer, включая секреты всех версий с шифрованием ключом целевой PostgreSQL.

#### Scenario: Обновление заполненной установки
- **WHEN** приложение запускается после обновления существующей БД
- **THEN** прежние объекты и история доступны, окружения имеют совместимые описания по умолчанию, а переменные, сертификаты, прежние статусы и причины сохранения сохранены

#### Scenario: Восстановление эталона из backup
- **WHEN** БД с изображениями и прогоном восстановлена в отдельную БД с исходным мастер-ключом и подготовленной demo-ролью
- **THEN** прежняя история показывает изображения и подписи, а сохранённые секреты ресурсов доступны выполнению без раскрытия браузеру

#### Scenario: Восстановление новых данных в тестовую схему
- **WHEN** тестовый backup с вариантами и незавершённой очередью восстановлен в свободное тестовое пространство общей БД
- **THEN** варианты, эталоны и результаты доступны, очередь прервана без повтора запросов, а рабочие данные не изменены

#### Scenario: Прежняя установка после добавления YAML
- **WHEN** qag обновлён и запущен с прежними PostgreSQL-параметрами
- **THEN** выбран PostgreSQL-backend, прежние данные/секреты доступны и YAML не создаётся
