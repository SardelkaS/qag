## MODIFIED Requirements

### Requirement: Единый локальный демонстрационный сервис

qag SHALL предоставлять демонстрационные HTTP- и unary gRPC-интерфейсы как часть обычного запуска приложения. Оба интерфейса MUST читать одну демонстрационную запись из выбранного хранилища приложения и возвращать согласованные идентификатор, название, статус и точную сумму. В нативном режиме демонстрационные адреса SHALL быть доступны только через loopback. В контейнерном режиме HTTP SHALL быть доступен через общий локально опубликованный порт qag, а gRPC SHALL быть доступен исполнителю запросов на loopback внутри контейнера без обязательной публикации порта. В PostgreSQL-режиме SQL-ресурс SHALL использовать то же PostgreSQL-хранилище под отдельной ограниченной ролью с адресом, достижимым из контейнера. В YAML-режиме служебная PostgreSQL MUST не требоваться; встроенный SQL SHALL сохраняться как запускаемый блок с явной ошибкой отсутствующей demo-БД при выполнении. Отдельный запуск сервиса пользователем MUST не требоваться.

#### Scenario: Согласованное чтение через два протокола
- **WHEN** пользователь запрашивает существующую демонстрационную запись через HTTP и gRPC
- **THEN** оба ответа содержат одинаковые значения из одной записи выбранного хранилища

#### Scenario: Запуск штатной сборки
- **WHEN** пользователь запускает настроенную готовую сборку qag
- **THEN** демонстрационные HTTP и gRPC доступны вместе с приложением без дополнительного процесса или контейнера

#### Scenario: Прохождение примера в Docker
- **WHEN** пользователь открывает опубликованный Web UI контейнерной установки и выполняет встроенный пример
- **THEN** HTTP, gRPC и SQL-блоки используют достижимые внутренние адреса и читают согласованную запись без запуска отдельного демонстрационного контейнера

#### Scenario: Пример без PostgreSQL
- **WHEN** qag работает с YAML на машине без PostgreSQL
- **THEN** демонстрационные HTTP/gRPC доступны и возвращают данные из файла, а SQL не подменяется другим протоколом

### Requirement: Отдельная постоянная демонстрационная схема

В PostgreSQL-режиме демонстрационные таблицы и начальная запись SHALL находиться в отдельной схеме `qag_demo` существующей БД qag. В YAML-режиме тот же набор начальных данных SHALL находиться в отдельном разделе общего файла и MUST не требовать схемы PostgreSQL. Перезапуск SHALL сохранять демонстрационные данные выбранного хранилища. Инициализация MUST не удалять и не заменять пользовательские папки, сценарии, ресурсы или историю. Демонстрационные публичные методы SHALL читать данные; их выполнение MUST не изменять демонстрационную запись.

#### Scenario: Добавление в существующую установку
- **WHEN** PostgreSQL-приложение с пользовательскими данными впервые запускается после обновления
- **THEN** схема и начальная демонстрационная запись появляются, а существующие пользовательские записи сохраняются

#### Scenario: Повторные обращения
- **WHEN** пользователь многократно вызывает демонстрационные методы и перезапускает qag
- **THEN** начальная запись остаётся доступной с теми же значениями без очистки или ручного сброса

#### Scenario: Повторная файловая инициализация
- **WHEN** qag несколько раз запускается с одним YAML
- **THEN** демонстрационная запись и системные ID не дублируются, пользовательские данные сохраняются

### Requirement: Контракт демонстрационного HTTP

HTTP SHALL предоставлять `GET /demo/v1/items/{id}`. Для `example-001` ответ SHALL иметь статус 200 и JSON с полями `id`, `name`, `status`, `amount`. `amount` MUST передаваться десятичной строкой без округления. Отсутствующая запись SHALL давать 404. Недоступное выбранное хранилище SHALL давать явную ошибку доступности; сервис MUST не подменять отказ PostgreSQL чтением YAML либо статическим успешным ответом. В явно выбранном YAML-режиме HTTP SHALL читать демонстрационный раздел файла.

#### Scenario: Известная запись
- **WHEN** выполняется `GET /demo/v1/items/example-001`
- **THEN** HTTP 200 возвращает `id=example-001`, `name=Локальный пример qag`, `status=ready` и `amount=9007199254740993.125`

#### Scenario: Отсутствующий идентификатор
- **WHEN** выполняется запрос для `missing-item`, отсутствующего в демонстрационной таблице
- **THEN** сервис отвечает 404, пригодным для обычного сравнения отрицательного результата

#### Scenario: HTTP из YAML
- **WHEN** в файловом режиме вызывается известный демонстрационный идентификатор
- **THEN** HTTP возвращает те же поля и точную сумму из YAML без подключения к PostgreSQL

### Requirement: Контракт демонстрационного gRPC

gRPC SHALL предоставлять unary-метод `qag.demo.v1.DemoService/GetItem` с идентификатором записи в запросе. Ответ SHALL содержать те же поля и точную сумму строкой, что и HTTP. Описание сервиса SHALL быть доступно через server reflection и поставляемый `.proto`. Отсутствующая запись SHALL давать `NOT_FOUND`; недоступное выбранное хранилище SHALL давать `UNAVAILABLE` без раскрытия реквизитов.

#### Scenario: Получение через reflection
- **WHEN** gRPC-блок вызывает `GetItem` с `{"id":"example-001"}` и использует reflection
- **THEN** результат имеет код `OK` и JSON-представление той же записи, что вернул HTTP

#### Scenario: Ожидаемое отсутствие записи
- **WHEN** gRPC-блок вызывает `GetItem` с `{"id":"missing-item"}`
- **THEN** результат имеет код `NOT_FOUND` и может совпасть с таким ожиданием

#### Scenario: gRPC из YAML
- **WHEN** в YAML-режиме вызывается GetItem через reflection
- **THEN** ответ согласован с HTTP и сохранённой записью файла без требования demo-DSN

### Requirement: Готовый сценарий трёх протоколов

qag SHALL автоматически подготовить один встроенный кейс «Пример: HTTP, gRPC и PostgreSQL» с описаниями действий и заполненными запросами и ожиданиями. Кейс SHALL проверять положительные HTTP/gRPC-ответы, SQL-чтение той же записи в PostgreSQL-режиме, ожидаемые HTTP 404 и gRPC `NOT_FOUND`, а также отдельное ручное действие. В YAML-режиме SQL-шаг SHALL оставаться видимым, доступным для ручного запуска и очереди, но его попытка SHALL завершаться явной ошибкой отсутствующей демонстрационной PostgreSQL без отправки запроса на случайный адрес. Подготовка прогона MUST разрешать исполнение остальных блоков; очередь SHALL продолжаться после SQL-ошибки. Ошибка исходного SQL MUST учитываться обычной оценкой прогона и MUST не превращаться в совпадение ожиданий. Первый и последующие прогоны SHALL использовать обычные правила ручных статусов, сравнения, снимков и сохранения истории.

#### Scenario: Первое прохождение
- **WHEN** пользователь в PostgreSQL-режиме открывает встроенный пример, выполняет все вызовы, отмечает ручные шаги как пройденные и завершает прогон
- **THEN** положительные и ожидаемые отрицательные вызовы совпадают, прогон получает `passed` и сохраняется по обычным правилам первых прогонов

#### Scenario: Повторное прохождение без подготовки
- **WHEN** пользователь начинает следующий прогон того же примера
- **THEN** он использует готовые ресурсы и те же стабильные данные выбранного режима без ручного редактирования запроса или БД

#### Scenario: Выполнить всё в YAML
- **WHEN** пользователь запускает все вызовы встроенного примера в YAML-режиме
- **THEN** HTTP/gRPC выполняются, SQL-попытка получает явную сохранённую ошибку, очередь продолжает остальные вызовы и ручные статусы не меняются автоматически
