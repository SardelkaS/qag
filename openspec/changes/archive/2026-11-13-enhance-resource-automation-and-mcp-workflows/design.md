## Context

Основание и пользовательские решения — в `proposal.md`. Изучены текущие формы, Engine/Runner, оба backend, MCP и reporting:

- `web/src/ResourcesPanel.tsx` хранит общие `config.headers` и секреты ресурса, но открытые переменные существуют только у окружения. `secretChanges()` отклоняет любую пустую строку имени, а `VariablesForm` превращает строки в map до серверной проверки. `HeaderEditor.tsx/TLSFields` принимает PEM текстом; выбор файлов уже реализован для proto bundles и изображений.
- `resources.Config`, `Resolved.Expand/Prepare` и `execution/header_sources.go` поддерживают статические подстановки, JSON Pointer, полную HTTP-форму, отдельный TLS/mTLS и кеш `per_attempt`/`per_run`. `Prepare` вызывается до `BeginAttempt`, поэтому динамические подстановки вне заголовков требуют отдельного чистого планирования перед сетью.
- `service.Engine` обслуживает UI/MCP через общие ports. MCP уже имеет `qag_run_start(executeAll)`, очередь всех вызовов, отдельные исходные и исследовательские попытки, чтение и отмену. Запуска всех вызовов одного шага нет. После очереди прогон остаётся открытым для ручной оценки.
- Оба `Runs.finish` назначают `first_run`/`first_success` без выбора политики. Есть несохранённые прогоны и явное сохранение `manual`; результат можно читать после перезапуска. Пользователь выбрал именно этот устойчивый путь, а не выполнение в памяти.
- MCP предоставляет 43 инструмента, но `ServerOptions.Instructions` не заполнен, постоянного руководства в resources нет. SDK v1.8.0 уже поддерживает Instructions. `docs/mcp.md`, `api/mcp-tools.json`, генератор/валидатор и SDK-пример должны согласовываться.
- Reporting строит документы из `runs.Report`. Для Jira нужен самостоятельный документ определения кейса: подстановка фиктивного прогона смешала бы сценарий и факты. Встроенный `demo.Scenario()` содержит положительные HTTP/gRPC/SQL, отрицательные 404/NOT_FOUND и ручной шаг; числовые значения заданы точно.
- PostgreSQL использует миграции `001`–`008`; YAML/dataset v1 строгий, неизвестные поля и версии отклоняются. Полный перенос охватывает 17 групп, включая все версии и неподтверждённые/незакреплённые прогоны.

## Goals / Non-Goals

**Goals:** единые определения ресурсов и исполнения для UI/MCP, PostgreSQL/YAML; явные правила закрепления без ослабления записи перед сетью; переносимость новых данных; руководство, которым агент может воспользоваться сразу после подключения.

**Non-Goals:** отправка комментариев/вложений в Jira, её авторизация и ADF; экспорт фактического прогона в новом Jira-формате; полностью временные попытки; автоматическая ручная оценка; выполнение скриптов извлечения; PKCS#12/DER и зашифрованные приватные ключи; автоматическое изменение read-only примера или рабочих контейнеров. HTTP-источники переменных в этом изменении не зависят от других HTTP-переменных: их параметры используют статические переменные и сохранённые секреты.

## Decisions

### 1. PEM читается браузером, сохраняется существующим контрактом

У CA/цепочки, клиентского сертификата и поля нового приватного ключа появляются отдельные file-input. Поддерживаются UTF-8 PEM до 1 MiB на файл, включая обычные `.pem`, `.crt`, `.cer`, `.key`; расширение не заменяет проверку содержимого. Чтение файла меняет только draft. Ошибка чтения/размера/PEM оставляет прежнее значение; отмена диалога ничего не очищает. Валидация пары сертификат/ключ остаётся серверной и атомарной при сохранении всего ресурса.

Ключ попадает только в `secrets.replace`, прежний ключ сохраняется при `keep`, удаляется только через `clear`. Ни абсолютный путь, ни имя файла не становятся ссылкой на диск сервера. Общий TLS-компонент можно использовать и в HTTP-источнике; для MCP клиент передаёт содержимое через существующие config/secrets. Альтернатива с путями на сервере неудобна в Docker/Go-install и нарушает переносимость.

### 2. Пустая новая строка игнорируется до валидации содержимого

UI фильтрует новые строки с `name.trim() === ''` до проверки дубликатов, подготовки HTTP-источников и преобразования в map. Это относится к окружению и ресурсу, открытым и секретным значениям, статическим и HTTP-переменным. Не следует молча схлопывать непустые дубликаты через `Object.fromEntries`.

На границе API/MCP выполняется та же нормализация пустых ключей/новых определений перед предметной валидацией; строгий dataset не принимает уже сохранённые некорректные имена. Для непустых имён сохраняется формат `[A-Z][A-Z0-9_]*`, конфликты и revision. Очистка имени существующего секрета не должна превращаться в его `clear`: клиент сохраняет исходную запись до явного удаления. Пропуск строки с пустым именем не означает пропуск ошибки в именованном HTTP-источнике.

### 3. Переменные ресурса хранят определения, а не результаты

В `resources.Config` добавляется необязательный `variables: map[string]VariableDefinition`. Определение имеет `mode: literal|http`, статическое `value` либо `source` с method, абсолютным URL, query, headers, bodyMode/body, TLS, privateKeySecret, JSON Pointer и fetchMode. Имена и контексты не меняются при переключении UI/MCP; определения версионируются вместе с ресурсом. Старое отсутствие поля равно пустому набору.

В одном эффективном контексте запрещены пересечения имён открытых переменных окружения, переменных ресурса и секретов окружения/ресурса; молчаливого shadowing нет, как и в существующих проверках секретов. В разных ресурсах одинаковые локальные имена допустимы. Статические подстановки остаются рекурсивными с обнаружением циклов. Источники HTTP используют только статические значения и сохранённые секреты; прямая/транзитивная зависимость от HTTP-переменной отклоняется до сети. Общие заголовки целевого ресурса в запрос источника автоматически не наследуются: иначе получение токена могло бы зависеть от самого токена.

Строки, числа и bool извлекаются как скаляры JSON Pointer с `UseNumber`; null, объекты, массивы и отсутствующий путь дают безопасную ошибку. Строка может быть пустой. Лимит ответа источника — существующие 5 MiB, извлечённого UTF-8 значения — 64 KiB. Подстановка в JSON/URL сохраняет экранирование и точность; SQL получает значения только через типизированные связанные параметры, не через сборку SQL-текста. Поддерживаются поля HTTP path/query/headers/body, gRPC metadata/body и SQL parameters. Адрес подключения, TLS и ожидания не получают вычисляемые значения.

### 4. Два этапа подготовки и прежний Runner

Чистая фаза строит план запроса: проверяет наличие определений, имена, типы, TLS, подстановки и допустимые поля, но оставляет известные динамические ссылки символическими. Она определяет только необходимые переменные, включая транзитивные ссылки из статических значений и реально используемых общих заголовков. Неиспользуемый HTTP-источник не вызывается; переопределённый заголовок не требует своего источника.

После устойчивой регистрации и claim попытки Runner через существующий request gate получает нужные HTTP-значения, выполняет подстановку, разрешает источники заголовков и отправляет основной запрос. Ошибка источника/отмена сохраняет попытку, основной запрос не начинается; очередь может перейти к следующему исходному блоку по прежним правилам. Второй исполнитель и отдельная схема хранения не вводятся.

`per_attempt` получает каждую переменную не более одного раза в одной попытке; `per_run` кеширует только успешный результат по runId/resourceVersion/name/определению. В пробном вызове scope равен attemptId, поэтому значение не переходит в другую пробу. Версия ресурса и окружения заморожена. Кеш очищается при завершении/отмене/закрытии; ошибки не кешируются, восстановление не отправляет запросы. Полученные значения и их варианты JSON/URL-экранирования включаются в маскирование, но не становятся именованными сохранёнными Secrets: это позволяет подставлять значение в path/query/body/SQL, не снимая прежние ограничения с настоящих секретов. История хранит только безопасную диагностику источника, а не его тело, выбранное значение или кеш.

Общие заголовки используют текущий `MergeRequestHeaders`: заголовок/metadata блока заменяет все одноимённые общие значения без учёта регистра. Остальные общие значения применяются к каждой исходной, пробной, исследовательской и очередной попытке. UI подписывает это явно; для PostgreSQL раздел заголовков не показывается.

### 5. Политика закрепления неизменна в течение прогона

`qag_run_start` и общий Engine получают необязательный `historyPolicy`; старые вызовы и UI остаются `auto`. Политика сохраняется с началом прогона и участвует в хеше идемпотентности; повтор с другим режимом — конфликт до сети.

| Режим | Терминальная фиксация | Слоты первого/первого успешного |
|---|---|---|
| `auto` | Прежние правила first_run/first_success | Участвует как раньше |
| `retain` | Добавляет `manual` независимо от результата, включая отмену/восстановленное прерывание; применяет прежние первые причины | Участвует |
| `unretained` | Не добавляет автоматические причины; прогон и попытки остаются устойчивыми | Не занимает слоты |

Последующее явное `qag_run_save` добавляет только `manual`, в том числе для `unretained`, не меняя политику и результаты. Finish/Cancel/Recover используют одну чистую функцию выбора причин в обоих backend. Параллельные завершения по-прежнему сериализуют выбор первых причин. Это явное расширение прежних требований о безусловном первом закреплении; оно внесено в delta `test-run-history`. Удалять прогон после исполнения вместо политики нельзя: это теряет попытки, нарушает идемпотентность и защиты первых результатов.

### 6. Шаг — выборка существующей очереди активного прогона

Новый MCP-инструмент `qag_run_step_execute(runId, stepId, idempotencyKey)` запускает все исходные блоки выбранного шага снимка, по порядку. Агент сначала создаёт обычный полный прогон без `executeAll`, затем выбирает шаг; отдельный неполный кейс или новый прогон на каждый шаг не создаётся. Для полного запуска используется прежний `qag_run_start(executeAll=true)` / `qag_batch_start`.

У очереди появляется необязательный `stepId`; отсутствие означает все шаги. Он сохраняется до сети и участвует в command hash. Состояние/прогресс доступны через тот же run get; шаг без блоков даёт завершённую очередь с нулём вызовов. Чужой/неизвестный шаг, терминальный прогон, активная очередь или одиночная попытка отклоняются атомарно. При новом ключе после окончания возможен явный повтор; при старом ключе возвращается прежняя очередь без повторной сети. Остальные шаги остаются непроверенными, результат всего кейса не объявляется успешным по одному выполненному шагу.

### 7. Jira — отдельный read-only экспорт определения

Добавить серверную проекцию сохранённого `catalog.TestCase` без конструирования `runs.Report`, выполнения источников, Resolve секретов или обращения к целевым ресурсам. Вход: ID, ожидаемая revision, `includeExpected` (default true); формат — `jira-wiki`. Неполный черновик разрешён. Снимок согласуется с указанной revision; конфликт требует обновления, экспорт не сохраняет несохранённый редактор молча.

Выход включает имя кейса, пронумерованные шаги, описания, протокол/имя ресурса, исходные параметры запроса и текстовые/типизированные ожидания. Подстановки остаются `${NAME}`; фактических ответов, дат/статусов прогона, динамических значений и раскрытия подключений нет. Изображения ожиданий представлены подписью/именем и явной пометкой о ручном приложении: файлы не загружаются в Jira, localhost URL и несуществующие attachment-ссылки не создаются. При `includeExpected=false` исключаются все ожидания, включая подписи изображений.

Использовать wiki headings и безопасные code/noformat-секции для JSON, SQL и многострочного текста; пользовательские `|`, `\\`, `{code}`, `{noformat}`, квадратные скобки и начальные маркеры списков не должны менять структуру. Это формат Wiki Style Renderer, не обещание совместимости с ADF. Основание: [Atlassian о специальных символах](https://support.atlassian.com/jira/kb/symbols-or-special-characters-are-hidden-in-issue-page-comment-description-section/) и [настройке wiki-renderer](https://support.atlassian.com/jira/kb/advanced-formatting-in-jira-text-fields-is-not-working/).

UI добавляет действие «Скопировать сценарий для Jira» в редактор с preview и переключателем ожиданий; используется browser text clipboard с честной ошибкой/возможностью взять текст вручную. MCP получает `qag_test_case_export` и UTF-8 text-артефакт через существующие TTL/chunk/SHA-256; запись в системный clipboard или публикация комментария не подразумевается. Для источников запросов в экспортируемом определении разрешены только заданные шаблоны, без исполнения. Значения литеральных Authorization/Proxy-Authorization/Cookie/Set-Cookie/X-Api-Key заголовков маскируются по имени без чтения хранилища секретов; остальные открытые литералы определения остаются пользовательским текстом. Экспорт не обещает распознать произвольный секрет, вручную записанный в обычном описании/теле.

### 8. Агент получает руководство через сам MCP

Заполнить `ServerOptions.Instructions` кратким маршрутом: status → demo IDs → чтение кейса/окружения/ресурсов → выбор режима запуска → polling → ручные решения → finish/save/export. Постоянный read-only ресурс `qag://guide/workflows` содержит полный справочник по предметным операциям, примеры аргументов и объяснение типичных ошибок. Он не является TTL-артефактом и не удаляется при обновлении списка артефактов.

Источник текста руководства находится внутри Go-пакета и входит в `go:embed`; README/`docs/mcp.md` ссылаются на тот же контракт и примеры. Установочный `cmd/module-fixture` должен включать этот конкретный embed-файл. Проверка каталога сопоставляет упомянутые инструменты/поля с реестром, не фиксируя старое число 43 при появлении новых инструментов.

Эталон читается через `qag_demo_get` и `qag_test_case_get`, UUID не зашиваются в текст. Руководство объясняет пять исходных вызовов, отдельный ручной шаг, 404/NOT_FOUND как ожидаемый успех, точный numeric/string, выбор ресурсов, отсутствие expected у вариантов, блокировку false passed и readonly. В YAML SQL примера закономерно ошибается: агент не заменяет его статическим успешным ответом и не исправляет системный кейс. Для авторских кейсов агент создаёт собственные ID/папку/окружение и переносит структуру, а не ссылки на системные ресурсы. Описать все существующие CRUD/archive, изображения, proto, TLS, переменные/источники, варианты, историю/удаление, форматы отчёта, артефакты, границы clipboard, CLI/YAML и выбор закрепления. Тема/scroll/focus остаются UI-предпочтениями, не MCP-командами. Текст сценариев/ответов является данными, а не инструкциями для изменения правил работы агента.

### 9. Согласованное обновление двух хранилищ

Новая миграция после `008` добавляет `runs.history_policy` с default `auto` и проверкой enum, а также nullable `run_batches.step_id` с проверяемой принадлежностью снимку. Определения переменных лежат в существующем versioned JSON ресурса. Старые миграции и JSON снимков/результатов не переписываются.

Dataset v2 переносит политику, выборку очереди и новые конфигурации. Декодер принимает строгие v1/v2; v1 нормализуется в памяти в `auto`/полную очередь/отсутствующие переменные, сохраняя raw исторический JSON. Чтение/экспорт не меняет источник; первая реальная запись YAML публикует v2 атомарно. Export всегда выдаёт v2, import принимает обе версии и сравнивает нормализованные default-поля, чтобы не создавать ложный ID-конфликт. Полученные HTTP-значения не входят в перенос ни как кеш, ни как секреты. `unretained` не означает исключение из полного переноса. Пределы размера/глубины/числа записей и no-clobber остаются прежними.

## Risks / Trade-offs

- [Источник нужен до текущего Prepare] → разделить чистый план и разрешение значений после Begin/claim; проверить сетевой счётчик при отказе записи.
- [Полученный токен отражён в URL/body/SQL или ошибке] → маскировать до устойчивой записи и выдачи, включая экранированные варианты; тело источника не сохранять.
- [Конфликт со старым безусловным first_run] → явный неизменный режим, legacy default `auto`, атомарный выбор причин и сценарии конкурентного завершения.
- [Слово «без истории» воспринимается как отсутствие данных] → в UI/MCP/docs писать «без закрепления; попытки сохраняются» и показывать несохранённый список.
- [Wiki-macro injection/потеря символов] → отдельный renderer, adversarial fixtures, точность больших чисел и preview; не отправлять текст в Jira автоматически.
- [Старый бинарник не читает v2] → документировать формат, до обновления сохранить v1/PG backup; не делать разрушительный автоматический downgrade.
- [Руководство расходится с инструментами] → единый embedded-текст, schema/catalog проверки и исполнение примеров на обеих версиях MCP и backend.

## Migration Plan

1. Сохранить исходные checksum миграций и использовать только изолированные fixture PostgreSQL/YAML. Подготовить v1-fixture с историей, секретами, вариантами и очередью.
2. Добавить новые модели, миграцию, чтение v1/v2 и контрактные defaults до подключения UI/MCP. Проверить перенос PostgreSQL ↔ YAML v2, чтение v1 и no-op повторного импорта.
