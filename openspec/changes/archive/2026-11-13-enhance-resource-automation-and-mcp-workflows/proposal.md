## Why

Настройка подключений требует ручной вставки PEM, динамические HTTP-значения доступны только заголовкам, а агенту недостаточно явных инструкций для полного прохождения сценария. Нужны удобная настройка ресурсов, экспорт определения кейса для Jira и управляемое выполнение через MCP с явно выбранным закреплением результата.

## What Changes

- Загрузка CA/цепочки, клиентского сертификата и приватного ключа из PEM-файлов в форме ресурса; ключ проходит существующий write-only механизм секретов. Прежняя вставка текста остаётся доступной.
- Экспорт только сохранённого определения тест-кейса в **Jira wiki markup** через UI и MCP: шаги, запросы и включаемые ожидания, без фактических результатов и обращения к Jira.
- Явный запуск всех исходных вызовов через MCP и новая команда последовательного выполнения вызовов выбранного шага активного прогона. Ручные статусы остаются ручными.
- Политика закрепления `auto` / `retain` / `unretained`: прежние вызовы используют `auto`; `retain` закрепляет терминальный прогон; `unretained` сохраняет прогон и попытки, но исключает автоматическое закрепление, включая первый и первый успешный. Позже результат можно сохранить вручную. Полностью временного выполнения нет.
- Обычные переменные ресурса и HTTP-источники значений: полная форма HTTP-запроса, JSON Pointer и выбор получения перед вызовом либо один раз на прогон. Подстановки доступны в параметрах HTTP/gRPC и связанных SQL-параметрах; полученные значения маскируются и не становятся сохранёнными секретами.
- Явный раздел общих HTTP-заголовков/gRPC-метаданных ресурса с сохранением существующего приоритета заголовка конкретного вызова. Общие заголовки уже поддержаны исполнителем; требуется сделать возможность заметной и проверить её во всех путях запуска.
- Пустые и состоящие из пробелов имена новых открытых, секретных и HTTP-переменных пропускаются при сохранении окружения/ресурса. Это не команда удаления существующего секрета; ошибки непустых имён и дубликатов сохраняются.
- Инструкции MCP при подключении и обнаруживаемое руководство по всем предметным возможностям; встроенный кейс служит эталоном структуры, типизации, отрицательных ожиданий и ручной оценки, оставаясь read-only.
- Совместимое обновление PostgreSQL и чтение прежнего YAML. **BREAKING для старых читателей:** новые файлы/экспорты используют YAML v2; новый qag читает v1 и v2, предыдущий qag не обязан читать v2.

## Capabilities

### New Capabilities

- `resource-http-variables`: переменные ресурса со статическим значением либо HTTP-источником, области подстановки, получение, ошибки и маскирование.
- `test-case-jira-export`: экспорт определения кейса в Jira wiki markup без запуска и истории, одинаковый для UI и MCP.

### Modified Capabilities

- `resource-environments`: PEM-файлы, общие заголовки, переменные ресурса и пропуск пустых новых имён.
- `mcp-server`: запуск шага, выбор закрепления, экспорт сценария и обнаруживаемые инструкции для агента.
- `test-run-history`: явная политика закрепления при сохранении попыток и совместимых defaults.
- `run-batch-execution`: последовательная очередь только исходных вызовов выбранного шага с прежними гарантиями записи и отмены.
- `yaml-data-storage`: новые определения/политики/выбор шага и совместимое чтение YAML v1 при записи v2.
- `portable-data-transfer`: полный перенос новых данных и нормализация legacy-defaults без получения динамических значений при импорте.

## Impact

Затронуты React-формы ресурсов/переменных и редактор кейса; Go-модели и подготовка ресурсов, Runner источников, Engine/очереди, оба репозитория прогонов, reporting, MCP DTO/описания/ресурсы, контракты OpenAPI/MCP/TypeScript, dataset/transfer и документация. Нужна новая миграция после `008`; старые миграции и прежняя история сохраняются. PostgreSQL и YAML получают одинаковое поведение, включая Go-install и Docker-поставку. Интеграции проверяются в изолированных схемах одной существующей БД, без изменения рабочего экземпляра.
