# local-app-runtime Specification

## Purpose

Локальный runtime предоставляет Web UI на TypeScript и Go-сервер с устойчивым PostgreSQL-хранилищем, чтобы тестировщик мог работать с каталогом и историей без учётной записи.

## Requirements

### Requirement: Локальный Web UI на Go и TypeScript

Приложение SHALL предоставлять браузерный UI на TypeScript и сервер на Go без формы входа для одного пользователя. Готовая сборка SHALL обслуживать UI и API одним Go-процессом. Нативный режим MUST слушать только loopback-интерфейс. Явно выбранный контейнерный режим SHALL разрешать listener, доступный перенаправлению Docker, при публикации HTTP только на loopback хоста в штатном Compose. Исполнение целевых HTTP-, gRPC- и SQL-вызовов SHALL происходить на сервере. Изменяющие состояние и исполняющие команды MUST не приниматься из постороннего веб-источника; настройка контейнерного режима MUST не отключать проверку Host, Origin и CSRF.

#### Scenario: Запуск и открытие UI
- **WHEN** пользователь запускает настроенное приложение и открывает его локальный адрес
- **THEN** появляется каталог тест-кейсов без страницы входа и доступен выбор раздела ресурсов

#### Scenario: Команда с постороннего сайта
- **WHEN** другая веб-страница пытается отправить команду запуска на локальный сервер приложения
- **THEN** сервер отклоняет её до выполнения внешнего запроса

#### Scenario: Контейнерный и нативный listener
- **WHEN** приложение настроено слушать все контейнерные интерфейсы
- **THEN** запуск разрешён только при явном контейнерном режиме, а нативная конфигурация по умолчанию сохраняет запрет такого listener

### Requirement: PostgreSQL как постоянное хранилище

Приложение SHALL хранить в PostgreSQL папки, сценарии, окружения, версии ресурсов, прогоны, статусы, комментарии, очереди, исследовательские варианты и подтверждённые результаты. Перезапуск приложения либо браузера MUST не терять успешно записанные данные. Штатная установка SHALL использовать одну физическую БД с рабочими и изолированными тестовыми схемами. Подключения, роли и пространства данных приложения и SQL-ресурсов SHALL задаваться явно, а исполнение блока MUST не использовать служебное подключение приложения по умолчанию.

#### Scenario: Данные после перезапуска
- **WHEN** пользователь сохранил тест-кейс, ресурс и прогон, затем перезапустил Go-процесс
- **THEN** каталог, настройки и сохранённая история загружаются из PostgreSQL в прежнем состоянии

#### Scenario: SQL-блок без целевого ресурса
- **WHEN** SQL-блок не имеет доступного PostgreSQL-ресурса в выбранном окружении
- **THEN** запуск завершается ошибкой подготовки, а запрос не отправляется в служебные таблицы приложения

#### Scenario: Тестовые и рабочие данные
- **WHEN** основной qag и тестовый экземпляр подключены к одной физической БД
- **THEN** каждый работает в своём пространстве схем и тестовые подключения не получают доступ к рабочему каталогу

### Requirement: Контролируемый запуск и миграции

При запуске приложение SHALL проверять конфигурацию, подключение к PostgreSQL, разрешённые схемы и поддерживаемую версию, применяя версионированные миграции только к своему пространству данных. До готовности SHALL быть подготовлены собственные демонстрационная схема, системный пример и ресурсы, а также запущены демонстрационные интерфейсы. Некорректная конфигурация, несовместимая схема либо недоступная БД MUST приводить к понятной диагностике без ложной готовности. Тестовый запуск MUST не подставлять рабочие схемы при отсутствии явной конфигурации. Пароли и ключ шифрования MUST не включаться в сообщения ошибки. Контейнерная установка SHALL ожидать успешную подготовку постоянной конфигурации, готовность PostgreSQL и подготовку ограниченной demo-роли; повторная подготовка MUST не менять исходные реквизиты.

#### Scenario: Первый запуск на пустой БД
- **WHEN** приложение запущено с корректным подключением к пустой выделенной PostgreSQL-БД
- **THEN** своё пространство создаётся миграциями, демонстрационный сервис и пример подготовлены, а интерфейс открывается с закреплённым примером и пустым пользовательским каталогом

#### Scenario: Недоступная БД при запуске
- **WHEN** PostgreSQL не отвечает либо аутентификация приложения не проходит
- **THEN** запуск сообщает безопасную причину и не открывает рабочий UI как успешно готовый

#### Scenario: Тестовый bootstrap
- **WHEN** тестовый экземпляр запускается в своих схемах общей БД
- **THEN** он подготавливает собственный пример и не меняет ID, ресурсы или историю рабочего примера

#### Scenario: Ошибка контейнерной подготовки
- **WHEN** подготовительный контейнер не смог сохранить конфигурацию или подготовить demo-роль
- **THEN** qag не объявляется healthy и не начинает внешние вызовы, а причина доступна без секретных значений

### Requirement: Устойчивость записи при работе

Система SHALL атомарно сохранять связанные изменения и SHALL не сообщать об успешном сохранении до подтверждения PostgreSQL. При недоступной БД введённый текст MUST оставаться в редакторе, а запуск нового внешнего вызова MUST быть запрещён, если не удалось устойчиво записать его начало. Потеря записи после уже отправленного вызова SHALL показываться как неопределённый результат без автоматического повторного исполнения.

#### Scenario: Ошибка сохранения сценария
- **WHEN** БД становится недоступна во время сохранения
- **THEN** UI показывает ошибку и сохраняет несохранённые правки пользователя для повторной попытки

#### Scenario: Нельзя записать начало вызова
- **WHEN** пользователь нажимает запуск, но сервер не может сохранить начало попытки в PostgreSQL
- **THEN** внешний ресурс не вызывается, а пользователь видит ошибку хранения

### Requirement: Инструкция локального развёртывания

Репозиторий SHALL содержать воспроизводимые инструкции сборки Go/TypeScript с иконкой, запуска одной PostgreSQL, подготовки изолированных тестовых схем/ролей, настройки подключения и ключа секретов, запуска приложения и выполнения проверок. README SHALL начинаться с актуального контейнерного запуска приложения и БД через Docker Compose, отдельно описывать эквивалентный запуск через Makefile и доступный адрес браузера. Для контейнерного пути SHALL быть достаточны Docker и Compose; GNU Make SHALL требоваться только для Make-варианта. Документация SHALL объяснять смену опубликованного порта, сохранение данных и ключа, импорт прежней установки и адреса ресурсов хоста при выполнении запросов из контейнера. Нативный Windows-режим SHALL оставаться описанным для разработки; его команды MUST работать в PowerShell. Документация SHALL описывать backup PostgreSQL и отдельного ключа/конфигурации, переход со старого тестового контейнера без удаления рабочего тома, ограничения локального режима и отсутствие гарантии отката внешнего действия при отмене. Платформенные возможности экспорта SHALL описываться согласно фактическому backend: Linux использует browser HTML clipboard, native Windows clipboard относится к нативному Windows-запуску.

#### Scenario: Настройка на чистой машине
- **WHEN** разработчик следует инструкции с установленными указанными инструментами и чистой PostgreSQL-БД
- **THEN** он собирает контейнерный образ, запускает UI и проходит демонстрационный ручной тест-кейс с локальными тестовыми ресурсами

#### Scenario: Проверки на общей БД
- **WHEN** разработчик выполняет документированные проверки рядом с рабочим приложением
- **THEN** используется один PostgreSQL-контейнер, тестовые объекты изолированы схемами и рабочие данные сохраняются

#### Scenario: Два способа контейнерного запуска
- **WHEN** пользователь выбирает в README прямой Docker Compose либо вариант с GNU Make
- **THEN** оба варианта приводят к одному адресу Web UI и одному сохраняемому состоянию без требования установить Go или Node.js на хост

### Requirement: Повторяемый жизненный цикл встроенного сервиса

Демонстрационные интерфейсы SHALL запускаться и завершаться вместе с процессом qag. В нативном режиме их слушатели MUST принимать соединения только через loopback. В контейнерном режиме демонстрационный HTTP SHALL использовать общий опубликованный локальный HTTP-порт qag, а gRPC SHALL оставаться на loopback внутри контейнера. Системные ресурсы SHALL использовать адреса, достижимые исполнителю запросов, а не wildcard-адрес listener. Занятый порт, недоступная демонстрационная схема либо некорректная отдельная SQL-учётная запись SHALL давать безопасную диагностику без ложной готовности. Повторный запуск SHALL сохранять идентичность встроенного кейса, окружения и истории и MUST не создавать повторные закреплённые элементы. Завершение приложения SHALL освобождать демонстрационные слушатели и подключения.

#### Scenario: Повторный запуск с историей примера
- **WHEN** пользователь завершил прогон встроенного кейса и перезапустил qag
- **THEN** кейс и сохранённая история имеют прежние идентификаторы, а в каталоге остаётся один закреплённый пункт

#### Scenario: Занят демонстрационный gRPC-порт
- **WHEN** заданный локальный gRPC-адрес занят другим процессом
- **THEN** qag сообщает о недоступном демонстрационном порте, не показывает готовность и освобождает уже созданные им слушатели

#### Scenario: Завершение и повторный запуск
- **WHEN** процесс qag штатно завершён, а затем запущен с прежними адресами
- **THEN** демонстрационные HTTP/gRPC снова доступны без оставшегося отдельного тестового процесса

#### Scenario: Внутренний адрес HTTP-примера
- **WHEN** HTTP-listener qag слушает все интерфейсы внутри контейнера
- **THEN** системный HTTP-ресурс указывает на достижимый локальный адрес внутри этого контейнера, а выполнение примера не обращается к wildcard-адресу

### Requirement: Светлая тёмная и системная тема

Web UI SHALL предоставлять светлую, тёмную и системную тему. Выбор SHALL сохраняться в браузере, применяться до первого отображения приложения и восстанавливаться после перезагрузки. При отсутствии явного выбора SHALL использоваться системное предпочтение; в системном режиме его изменение SHALL обновлять тему. Все разделы, формы, диалоги, статусы, SQL-таблицы, изображения и сравнение результатов SHALL оставаться читаемыми. Переключение MUST не менять сценарий, окружение, текущий прогон или несохранённые правки.

В тёмной теме основные поверхности, фон страницы, боковая панель, карточки, поля, границы и вторичный текст SHALL использовать нейтральные графитовые и серые оттенки без преобладающего зелёного тона. Зелёный SHALL сохраняться как ограниченный акцент бренда и успешного результата. Текст, границы, фокус и три ручных статуса MUST оставаться различимыми; обычный текст SHALL иметь контраст с фоном не менее 4,5:1.

#### Scenario: Явная тёмная тема
- **WHEN** пользователь выбирает тёмную тему и перезагружает страницу
- **THEN** все разделы открываются в тёмной теме без предварительного отображения светлого интерфейса

#### Scenario: Системное предпочтение
- **WHEN** выбран системный режим и системная тема меняется
- **THEN** интерфейс следует новому предпочтению без потери введённых данных

#### Scenario: Переключение во время редактирования
- **WHEN** пользователь переключает тему с несохранёнными изменениями и открытым результатом вызова
- **THEN** содержимое редактора, выбранное окружение и показанная попытка остаются прежними

#### Scenario: Нейтральная тёмная палитра
- **WHEN** пользователь открывает каталог, редактор, ресурсы, прогон и диалог в тёмной теме
- **THEN** большие поверхности выглядят графитовыми или серыми, текст остаётся контрастным, а зелёный ограничен небольшими акцентами и успешными результатами

#### Scenario: Тёмная палитра в системном режиме
- **WHEN** выбрана системная тема и операционная система использует тёмное оформление
- **THEN** применяется та же нейтральная палитра, что и при явном выборе тёмной темы, а светлый режим остаётся доступным

### Requirement: Совместимое обновление и резервное копирование новых данных

Обновление SHALL сохранять существующие кейсы, окружения, переменные, секреты, TLS/mTLS-конфигурации, встроенный пример, прежние ручные статусы и историю. Старые записи SHALL получать совместимые значения новых необязательных полей без переписывания снимков. PostgreSQL-backup SHALL включать изображения, описания окружений, варианты, версии их запросов и данные очередей вместе с историей. Восстановление с исходным ключом SHALL позволять читать эталоны и использовать прежние секреты. Полученные заголовки MUST не становиться открытыми данными backup. Восстановленный незавершённый прогон MUST не возобновлять внешние действия автоматически.

#### Scenario: Обновление заполненной установки
- **WHEN** приложение запускается после обновления существующей БД
- **THEN** прежние объекты и история доступны, окружения имеют совместимые описания по умолчанию, а переменные, сертификаты, прежние статусы и причины сохранения сохранены

#### Scenario: Восстановление эталона из backup
- **WHEN** БД с изображениями и прогоном восстановлена в отдельную БД с исходным мастер-ключом и подготовленной demo-ролью
- **THEN** прежняя история показывает изображения и подписи, а сохранённые секреты ресурсов доступны выполнению без раскрытия браузеру

#### Scenario: Восстановление новых данных в тестовую схему
- **WHEN** тестовый backup с вариантами и незавершённой очередью восстановлен в свободное тестовое пространство общей БД
- **THEN** варианты, эталоны и результаты доступны, очередь прервана без повтора запросов, а рабочие данные не изменены
