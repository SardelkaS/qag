# qag

Локальное приложение на Go и TypeScript для создания и ручного прохождения тест-кейсов с HTTP-, gRPC- и PostgreSQL-вызовами. Один пользователь, без авторизации.

Есть каталог с папками и архивом, редактор шагов, окружения и ресурсы с TLS/mTLS, сравнение ожидаемого и фактического ответа, ручные статусы и история. Первый завершённый и первый успешный прогон закрепляются автоматически, остальные — по кнопке. Сценарии, попытки и прогоны хранятся в PostgreSQL.

Незавершённые кейсы сохраняются как черновики без обязательных полей. К ожидаемому результату шага или вызова можно приложить изображения для ручного сравнения. Ресурс выбирается из списка; заголовки умеют получать значение из JSON отдельного HTTP-запроса перед каждым вызовом или один раз на прогон. Доступны светлая, тёмная и системная темы.

«Выполнить всё» запускает исходные вызовы последовательно и продолжает после ошибок; ручные отметки остаются за пользователем. Прогон можно отменить сверху. Исследовательские варианты запросов сохраняются вкладками, со всеми версиями и попытками, и не влияют на официальный итог. Результат экспортируется в PDF, текст, Markdown или оформленный текст с изображениями вызовов для Word/почты; ожидаемые результаты можно исключить.

## Запуск через Docker Compose

Нужны Docker Engine с Linux-контейнерами и Docker Compose v2 (в Windows — Docker Desktop). Go, Node.js и PowerShell для этого способа не требуются.

```console
docker compose up --build -d --wait
```

Откройте **http://127.0.0.1:8080**. Compose собирает Web UI и Go-бинарник, сохраняет случайные реквизиты/PKI в именованных томах, запускает одну PostgreSQL и подготавливает demo-роль. qag работает непривилегированным пользователем; готовность включает БД и встроенные интерфейсы.

При занятом порте задайте `QAG_HTTP_PORT=18088` в окружении перед той же командой. В PowerShell:

```powershell
$env:QAG_HTTP_PORT = '18088'
docker compose up --build -d --wait
```

В POSIX shell: `QAG_HTTP_PORT=18088 docker compose up --build -d --wait`. Адрес станет **http://127.0.0.1:18088**. Публикация остаётся на loopback хоста; demo gRPC доступен только внутри контейнера.

```console
docker compose ps -a
docker compose logs -f qag postgres
docker compose down
```

`down` сохраняет БД, мастер-ключ и PKI. Для повторного запуска используйте первую команду. Тома `qag_postgres-data`, `qag_runtime-config`, `qag_private-pki` и `qag_postgres-config` составляют одну установку.

### Вариант с GNU Make

При установленном GNU Make:

```console
make help
make up
make up QAG_HTTP_PORT=18088
make down
```

Остальные цели: `init`, `build`, `restart`, `logs`, `ps`, `import-local`. Они вызывают тот же Compose без Bash/PowerShell в рецептах. Прямые команды Docker доступны без Make.

### Переход с нативной установки

Сначала завершите или отмените активные прогоны, остановите нативный qag и сохраните dump БД вместе с исходными `.local/dev.env` и `.local/pki` по [инструкции](docs/operations.md). Затем:

```console
docker compose --profile tools run --build --rm --no-deps import-local
docker compose up --build -d --wait
```

Импорт сохраняет исходный ключ, пароли и demo-роль, переводя только поддерживаемые локальные подключения `127.0.0.1:15432/qag` на `postgres:5432/qag`. Старый `qag_postgres-data` используется повторно; исходные файлы и пользовательские ресурсы не меняются. Старая БД без конфигурации, конфликт ключей или несовместимый TLS вызывают отказ до замены реквизитов.

`127.0.0.1` в пользовательском ресурсе теперь означает контейнер qag. Для ресурса хоста используйте `host.docker.internal` (Compose добавляет Linux host-gateway); целевой сервер должен слушать адрес, доступный Docker. Для соседнего контейнера укажите его DNS-имя и внутренний порт. Настройте соответствующие сертификаты обычным способом.

## Нативная разработка в Windows

Нужны Go 1.26+, Node.js 24.18+ и работающий Docker Desktop с Compose и Linux Engine. Используется PostgreSQL 18.6 с ICU для [русской сортировки](https://www.postgresql.org/docs/18/collation.html). Зависимости закреплены в `go.mod` / `go.sum` и `web/package-lock.json`.

В PowerShell из корня репозитория:

```powershell
docker compose stop qag
.\scripts\init-local.ps1
.\scripts\database.ps1 -IncludeTests
.\scripts\build.ps1
.\scripts\run.ps1
```

Откройте **http://127.0.0.1:8080**. `dist/qag.exe` содержит UI; отдельный Node/Vite-процесс для работы не нужен. Для повторной сборки: `scripts/build.ps1 -SkipInstall`.

Скрипт `init-local.ps1` импортирует прежнюю конфигурацию либо подготавливает Docker-состояние и экспортирует те же реквизиты/PKI в `.local`; конфликтующий файл не перезаписывается. `database.ps1` запускает только PostgreSQL и подготовку роли, используя один сервер. `.local/dev.env` исключён из Git и содержит тот же мастер-ключ. Для изолированного E2E рабочий qag останавливать не нужно.

## Первый сценарий

Нажмите **«Встроенный пример»** над папками. Готовый кейс проверяет одну запись через HTTP, gRPC и PostgreSQL, ожидаемые ошибки отсутствующей записи и ручной итог. Нажмите «Начать прогон», выполните вызовы и отметьте шаги. Настраивать ресурсы не требуется. Сценарий доступен для просмотра и запуска, его системное окружение выбирается автоматически.

Демонстрационный сервис входит в процесс qag: HTTP — `/demo/v1` на основном адресе, gRPC с reflection — `127.0.0.1:9091` (в Docker это внутренний loopback). Данные находятся в схеме `qag_demo` той же БД `qag`. Пароль отдельной SQL-роли хранится как зашифрованный секрет ресурса.

Для собственного сценария:

1. В «Окружения и ресурсы» создайте окружение: имя и необязательное описание. Переменные настраиваются рядом с HTTP/gRPC/PostgreSQL-ресурсами.
2. Создайте папку и тест-кейс, добавьте шаги с описанием и блоки вызовов.
3. Укажите ресурс, параметры и ожидаемый результат. Сохраните сценарий.
4. Для отдельной проверки нажмите «Запустить вызов», для полного прохождения — «Начать прогон».
5. Выполните вызовы, выставьте ручные статусы, сохраните комментарии и завершите прогон.

Примеры `AI_GW_SERVISE/task`, переменные, сертификаты и правила истории — в [инструкции](docs/usage.md). Резервные копии, ключ и диагностика — в [эксплуатации](docs/operations.md).

## Конфигурация

| Переменная процесса | Значение |
|---|---|
| `QAG_CONFIG_FILE` | Приватный JSON установки; заданный невалидный файл вызывает отказ; переменные процесса переопределяют его значения |
| `QAG_NETWORK_MODE` | `native` по умолчанию; `container` разрешает wildcard-listener с обязательным публичным origin |
| `QAG_PUBLIC_ORIGIN` | Локальный HTTP-origin опубликованного порта, в Compose задаётся автоматически |
| `QAG_HTTP_PORT` | Порт хоста Compose/Make, по умолчанию `8080` |
| `QAG_DATABASE_URL` | Рабочая PostgreSQL-БД `qag` |
| `QAG_DEMO_DATABASE_URL` | Та же БД и сервер под отдельной ограниченной ролью; обязательна |
| `QAG_DEMO_GRPC_ADDRESS` | По умолчанию `127.0.0.1:9091`, только loopback; порт `0` для тестов |
| `QAG_SECRET_KEY` | Мастер-ключ AES-256-GCM: 32 байта в base64, вне БД |
| `QAG_ADDRESS` | Нативный default `127.0.0.1:8080`, только loopback; Compose задаёт `0.0.0.0:8080` |
| `QAG_DEV_ORIGIN` | Только для Vite, например `http://127.0.0.1:5173` |
| `QAG_TEST_DATABASE_URL` | Provisioning-подключение к той же `qag`; ограниченные роли и уникальные схемы создаёт fixture |
| `QAG_SCHEMA` / `QAG_DEMO_SCHEMA` | В тестовом режиме — связанные имена `qag_test_<32 hex>` / `<app>_demo` |
| `QAG_TEST_MODE` | `1` для тестового экземпляра; рабочие defaults — `qag` / `qag_demo` |
| `QAG_TEST_PKI_DIR` | Путь `.local/pki` для проверки клиентских сертификатов PostgreSQL |

Для внешней PostgreSQL настройте оба подключения в `.local/dev.env` либо в окружении процесса. Нужны права создания схем, таблиц и ICU collation. Demo-роль подготавливается отдельно администратором; порядок описан в [эксплуатации](docs/operations.md). Миграции применяются автоматически до readiness; на пользовательских SQL-целях они не запускаются. Один экземпляр владеет своим пространством схем; рабочее и разные тестовые пространства могут работать одновременно.

Для Vite загрузите оба подключения и ключ в окружение Go-процесса, задайте `QAG_DEV_ORIGIN=http://127.0.0.1:5173`, запустите backend и выполните `npm.cmd run dev` в `web/`. Dev proxy направляет API на `127.0.0.1:8080`.

## Проверки

```powershell
.\scripts\database.ps1 -IncludeTests
.\scripts\verify.ps1
```

Общий сценарий воспроизводит protobuf bindings, устанавливает зависимости по lockfile, собирает встроенный UI, проверяет контракт, выполняет Go test/vet, Vitest, интеграционные проверки PostgreSQL, backup/restore, Playwright в Chromium и строгую валидацию OpenSpec. Рабочие ресурсы пользователя не используются.

Отдельные команды:

```powershell
.\scripts\proto.ps1
.\scripts\contracts.ps1
.\scripts\test-integration.ps1
.\scripts\test-e2e.ps1
.\scripts\test-container.ps1
```

Перед отдельным E2E соберите frontend через `scripts/build.ps1 -OutputPath .local/verify/qag.exe`. Стенд создаёт уникальные схемы и ограниченные роли в `qag`, HTTP/gRPC-цели и сертификаты. Compose использует единственный PostgreSQL на 15432; старый тестовый том сохраняется при переходе. `verify` собирает отдельный бинарник и не перезаписывает работающий `dist/qag.exe`. Результаты — [docs/verification.md](docs/verification.md).

`test-container.ps1` собирает Linux-образы и проверяет опубликованный порт 18088, UI, полный встроенный пример, экспорт из Chromium, SIGTERM и recreate. Для этих проверок нужны Go, Node.js и зависимости `web`/Playwright на хосте; штатный Compose-запуск их не требует. Создаются только уникальные тестовые схемы/роли той же БД. Linux-backend использует browser HTML clipboard с PNG; native RTF/Windows clipboard доступен при нативном Windows-запуске.

## Пределы первой версии

Поддерживаются HTTP, unary gRPC с reflection или proto bundle и PostgreSQL. Тайм-аут 1–300 секунд, ответ до 5 MiB, SQL до 1000 строк. JSON и decimal сравниваются без округления больших чисел. Шаги и блоки идут в авторском порядке; каталог — по алфавиту, история — от новых к старым.

Внешние вызовы автоматически не повторяются. Отмена, тайм-аут и потеря процесса могут оставить внешний эффект; сначала проверьте целевую систему. Прерванные прогоны восстанавливаются с явным статусом без повторного исполнения. Секреты вводятся через отдельные поля и маскируются в результатах.

Скриптов, streaming gRPC, расписаний, CI и многопользовательского режима в этой версии нет.

Завершённое изменение — [add-manual-testing-app](openspec/changes/archive/2026-10-25-add-manual-testing-app/proposal.md); все [52 задачи](openspec/changes/archive/2026-10-25-add-manual-testing-app/tasks.md) выполнены. Актуальные контракты находятся в [openspec/specs](openspec/specs).

Встроенный сервис и закреплённый пример реализованы в [add-local-demo-service](openspec/changes/archive/2026-10-26-add-local-demo-service/tasks.md): все 25 задач выполнены, спецификации синхронизированы, изменение архивировано.
